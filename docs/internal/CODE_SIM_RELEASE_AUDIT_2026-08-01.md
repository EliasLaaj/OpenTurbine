# OpenTurbine v2.0.1 code and simulation release audit

**Audit date:** 2026-08-01
**Repository:** `elia179/OpenTurbine`
**Commit audited:** `afaf4c9192f1fe0333120c1f40494b37e9dd7775` (`main`, tag/release `v2.0.1`)
**Scope constraint:** No physical ECU, engine, harness, or sensors were available. This report is based on source review, host-side tests and fuzzers, firmware builds, static analysis, release-artifact inspection, GitHub configuration, and browser-oriented UI checks. It does not claim hardware qualification.

**Audit policy:** OpenTurbine deliberately supports unusual, externally assisted, sensor-light, and fully custom installations. A strange setting or sequence is not a defect merely because it differs from a conventional turbine setup. Yellow warnings and an explicit **Save anyway** path are valid product behavior when the choice remains internally coherent and cannot bypass the ECU's hard combustion cut, STOP, fault/all-off, reset-recovery, or hardware-protection boundaries. Findings below are reserved for broken hard invariants, silent contract mismatches, misleading authoritative state, invalid persistence/concurrency behavior, or release/integration gaps. Advisory design risks are identified separately and must not be used to remove expert freedom without a demonstrated hardware-protection need.

## Executive verdict

The repository's full local release gate passes, both firmware targets build within their configured budgets, the Setup Tool tests pass, the published hashes are internally consistent, and the dashboard audit suite passes. Those results are useful but are not sufficient to flash this build to tester ECUs yet.

Four confirmed control-path defects should be treated as **P0 release blockers**, with a fifth P0/P1 escalation defect requiring the same pre-flash attention:

1. An automatic sensor-fault reduced-power state can be cleared by an unrelated manual or configured `limp_mode` input after the safety check but before throttle protection in the same loop iteration.
2. A profile-backed registry START switch held during boot can be mistaken for a new press after the first registry sample, defeating the documented release-after-boot interlock.
3. A disabled Control Rule still applies its configured `off_value`; a nonzero value can energize an actuator even though the dashboard says the rule is disabled.
4. A web/cluster STOP placed ahead of an already queued START does not cancel that START, so the ECU can process STOP in STANDBY and then start in the same queue drain.
5. After an ordinary mid-run feedback loss latches reduced power, subsequent required-sensor losses do not escalate because the detector stops evaluating while `limpMode` is set.

Another serious issue is the default open, unauthenticated ECU access point. Any associated client can call actuator/start/configuration/update endpoints directly and can enable Developer Mode and Bench Mode without the dashboard's confirmation UI. For tester distribution, this needs either a code-level commissioning control or a hard release requirement to provision a strong AP password before operation.

The focused afterburner follow-up adds five P1 control-envelope findings: the main-fuel AB offset bypasses gradual throttle protection, a stuck-high/transient flame detector can false-confirm, stabilization can lose evidence yet declare Running, custom light-up has no independent fuel-on deadline, and the existing custom-order defect compounds all of these. EGT-rise timing, trigger conditioning, diagnostics, legacy switch semantics, and the throttle request/permission ownership error add P2 work. The separate operator-trigger assessment and opportunity table propose more useful hobby-turbine controls without treating sensorless/timed operation, dedicated switches/axes, or expert sequencing as defects.

## Confirmed control and safety findings

### OT-AUD-001 — automatic reduced-power state can be cleared

Limited START deliberately records the failed sensor in `limpOverrideSensor` and sets `limpMode = true` in `src/main.cpp:2570-2572`. Throttle feedback enforcement ignores the selected failed sensor while the override is active, and the reduced-power cap/freeze logic is gated by `limpMode` in `src/Hardware.h:2355`, `src/Hardware.h:2365`, and `src/Hardware.h:2758`.

There are three independent ways to clear that Boolean without clearing the sensor override:

- `TOGGLE_LIMP_MODE` is accepted in STANDBY or RUNNING by `src/system/web/WebServer.cpp:387-389` and toggles the Boolean directly in `src/main.cpp:2620-2624`. The same command is also exposed as unauthenticated cluster-serial text command `OTC:CMD,LIMP_TOGGLE` (`src/system/ClusterSerial.cpp:732-739`), so this is not limited to the Tools page.
- A native `limp_mode` digital input clears it on its falling edge in `src/main.cpp:1572-1580`.
- A healthy registry `limp_mode` channel assigns `ed.limpMode = active` on every tick in `src/main.cpp:1594-1613`; an installed but inactive switch therefore continuously clears an automatically imposed state.

The ordering makes this immediately safety-relevant. `g_safety.check()` runs at `src/main.cpp:3398`, `checkGeneralDI()` can clear the flag at line 3411, then throttle protection and actuator updates consume the cleared flag at lines 3418 and 3421. Thus the automatic cap can be removed in the same tick while the failed feedback remains explicitly ignored.

Required regression cases:

- limited START with each eligible single failed sensor, no limp input configured;
- the same with inactive/active native and registry limp inputs;
- Tools toggle while RUNNING under automatic override;
- switch transitions during the override;
- a second feedback failure must still stop safely;
- leaving RUNNING must clear both the override identity and all automatic/manual sources deterministically.

The implementation should model automatic reduced-power demand and operator-requested limp as separate sources, with the effective protection equal to their logical OR. A manual control must never be able to negate an automatic safety demand.

### OT-AUD-002 — registry START held at boot can auto-start

The official S3 PCB profile assigns START to a TCA9554 registry input (`pcb_profiles/official/openturbine-ecu-s3-v1.otpcb.json:207`). Registry input health/value is consumed by `registryControlInput()` in `src/main.cpp:2964-2977`.

On the first control-loop iteration, `checkStartSwitch()` runs before `Hardware::updateSensors()` (`src/main.cpp:3375-3381`). Registry health is initially false, so a physically held START is observed as not pressed. The initialization block then sets `startReleasedSinceBoot = true` (`src/main.cpp:3042-3051`). Once the first registry sample becomes healthy, the still-held switch looks like a new rising edge and queues START (`src/main.cpp:3053-3067`). A disconnect/reconnect while the switch is held can produce the same class of false edge.

The web/core preflight's release gate is additionally conditioned on `HardwareConfig::startPin >= 0` (`src/system/web/WebServer.cpp:446-448` and the corresponding command path), which does not represent a registry-only START input.

Required regression cases:

- START released throughout boot;
- START held before power-on and through registry discovery;
- registry unavailable at boot, then appears released;
- registry unavailable at boot, then appears held;
- healthy registry disconnect/reconnect while released and while held;
- active-high and active-low native START variants;
- no START may be queued until one positively observed healthy released state has occurred.

### OT-AUD-016 — disabled rules can still energize outputs

`RulesEngine::evaluate()` calculates `activeState` from the rule's enabled flag and mode mask (`src/system/RulesEngine.h:84-94`), but initializes demand to the configured `offValue` and applies that demand even when `activeState` is false (`src/system/RulesEngine.h:95-118`). Applying `offValue` outside the selected modes and for an unavailable input is documented behavior (`docs/USER_GUIDE.md:444-448` and the rendered Control Rules introduction), so that part is not classified as a defect. Applying it when `enabled == false` is different: the public guide says **Enabled** makes the rule active, while disabling it does not release or zero the target.

The configuration layer accepts `off_value` across the full 0..1 range (`src/system/Config.cpp:909-926`) and retains disabled rules during sanitization (`src/system/Config.cpp:1205-1232`). A disabled rule can therefore continue to own its target and command a nonzero value indefinitely.

Disabled rules also participate in duplicate-target ownership. The sanitization pass checks and claims each non-request target without first requiring `r.enabled` (`src/system/Config.cpp:1208-1229`). An imported configuration with a disabled rule first and an enabled rule for the same target second passes the server's basic schema/ID validation; sanitization keeps the disabled owner and silently drops the enabled rule. The dashboard prevents duplicate targets during ordinary editing, but restore/import and older files still reach the firmware path.

This reaches physical outputs. Rules execute after controllers and general inputs (`src/main.cpp:3415-3418`), and `Hardware::updateActuators()` then writes the resulting demands. STANDBY has no final all-off invariant on each tick; `Hardware::allOff()` is called at the transition into STANDBY, after which the disabled rule runs again on subsequent loops. Examples include fuel shutoff, igniters, starter enable/demand, throttle, air starter, and registry outputs (`src/system/RulesEngine.h:342-386`). A disabled rule with `off_value = 1` can therefore command a fitted binary actuator ON while the ECU reports STANDBY.

Shutdown was checked as a related path: `Hardware::applyShutdownCombustionInvariant()` forcibly clears combustion demands at the final actuator boundary (`src/Hardware.h:1115-1138`), so the same rule cannot reopen combustion during SHUTDOWN. That protection does not resolve STANDBY or make disabled/out-of-state rule behavior correct.

Required regression matrix:

- enabled and disabled rules, with disabled rules required to release/zero their target;
- condition true, false, and sensor unhealthy;
- each mode: STANDBY, STARTUP, RUNNING, SHUTDOWN, and FAULT;
- `off_value` equal to zero and nonzero;
- every hazardous core target plus a generic registry output;
- changing, disabling, and deleting a rule must release ownership to a physical zero unless another explicit in-state owner exists;
- the UI's selectable modes must exactly match the firmware's persisted/effective mask.

### OT-AUD-017 — Standby rule state is silently discarded

The rendered Control Rules editor exposes a **Standby** checkbox and includes bit `1` in the saved `mode_mask` (`data_src/sequence.html:3352` and `data_src/sequence.html:3529`). Its save validation accepts any nonzero mask (`data_src/sequence.html:3589`), and firmware JSON validation accepts masks from 1 through 14 (`src/system/Config.cpp:924`). Firmware sanitization then unconditionally removes the Standby bit with `r.modeMask &= 0x0E`; if Standby was the only selected state, the whole rule is silently dropped (`src/system/Config.cpp:1225-1226`).

The public guides describe rule states as Starting, Running, and Shutdown—not Standby (`docs/USER_GUIDE.md:444` and `site/user-guide.md:429`). Thus the UI is the inconsistent layer. A user can configure and save a state that never takes effect, and a Standby-only rule can disappear after save/reboot without a validation error.

### OT-AUD-018 — advisory: nonzero fallback demands outside active modes

For an enabled rule, applying `off_value` when its condition is false is useful and documented. The implementation also applies that same value when the current mode is outside the rule's selected states (`src/system/RulesEngine.h:90-118`; `docs/USER_GUIDE.md:444-448`). The UI permits a logical ON/nonzero fallback and permits hazardous targets including throttle, starter, starter enable, main fuel shutoff, igniters, afterburner fuel, and air starter (`data_src/sequence.html:3030-3050` and the rendered Output list).

Consequently, a Running-only rule with `off_value = On` can hold its hazardous target on throughout STANDBY. This occurs after the one-time `Hardware::allOff()` transition and is written by the normal final actuator update. The UI and guides mention the generic off-value behavior but do not warn that selecting a nonzero fallback for these targets defeats the ordinary meaning of Standby/all-off. SHUTDOWN's final combustion invariant prevents reopening combustion there, and FAULT explicitly forces rule targets to zero; neither protects STANDBY.

On recheck against the project's stated flexibility policy (`docs/USER_GUIDE.md:5`), this is intentional expert behavior rather than a release defect. Nonzero fallback can be useful for pumps, valves, pitch, or installation-specific logic, and blanket zeroing would change the rule's documented meaning. Preserve it. The appropriate improvement is a high-consequence warning and explicit final-state preview when a combustion, ignition, or starter target has a nonzero out-of-state value, so the operator knowingly accepts the persistent command. OT-AUD-016 remains a defect because a rule marked **disabled** is a different contract and must not retain ownership through its fallback.

### OT-AUD-019 — Setup Tool clipboard allocation leak

The Windows Setup Tool allocates movable global memory and transfers ownership to `SetClipboardData` in `setClipboardText()` (`tools/setup_tool/main.go:1478-1503`). If `GlobalLock` fails, or if `SetClipboardData` fails after unlock, the function returns without calling `GlobalFree`; no `GlobalFree` procedure is loaded elsewhere. This is a low-frequency, low-severity desktop resource leak on support-log copy failure, not an ECU safety issue.

### OT-AUD-020 — singleton registry purposes are enforced only by the dashboard

The Hardware UI defines singleton input/output purposes—including primary N1/N2/EGT/oil sensors, START, STOP, throttle/idle, main fuel, fuel shutoff, starter, ignition, oil pump, and prop pitch—and blocks duplicates (`data_src/hardware.html:2802-2822`). Firmware `ChannelRegistry::add()` rejects duplicate IDs and endpoints but does not reject duplicate singleton purposes; `ChannelRegistry::validate()` likewise checks per-channel validity and endpoint collisions, not purpose uniqueness (`src/system/ChannelRegistry.h:259-334`). Full restore/import therefore accepts a configuration the ordinary dashboard will not create.

The resulting ownership is not uniformly resolved. `registryControlInput()` returns the first matching START/STOP purpose (`src/main.cpp:2964-2977`), while PCB/legacy control-field reconciliation loops across all inputs and leaves the last matching START/STOP channel in the mirrored fields (`src/system/HardwareConfig.cpp:1393-1398` and `src/system/HardwareConfig.cpp:3764-3773`). Other singleton adapters commonly use first-match lookup. A restored duplicate can therefore make configuration validation/status describe one channel while the live control path consumes another.

Firmware must enforce the same singleton-purpose set as the UI before accepting hardware patches or full restores. Add restore tests for duplicate START, STOP, every primary feedback purpose, and every core actuator purpose; the file should be rejected atomically with the previous configuration retained.

### OT-AUD-021 — restore staging failure leaves a rejected registry live

The full-engine restore deliberately passes the live `HardwareConfig::channelRegistry` as scratch space to `HardwareConfig::validateJson()` (`src/system/web/WebServer.cpp:3141-3145`). Validation calls `ChannelRegistry::fromJson()` on that workspace before checking the remaining hardware dependencies and pins (`src/system/HardwareConfig.cpp:3154-3186`), so successful validation has already replaced the runtime registry with the uploaded one.

Most later rejection paths call `restoreHardwareRuntime()`, which reapplies the pre-upload snapshot. One path does not: if opening or completely serializing `/ecu_config.hardware.tmp` fails, the handler returns HTTP 500 after `_finishConfigRestore()` without restoring the old hardware runtime (`src/system/web/WebServer.cpp:3155-3167`). The authoritative `ecu_config.json` remains unchanged, but the ECU continues running until reboot with old scalar hardware fields and the rejected upload's channel registry. That split state can alter which START/STOP, feedback, and output channels the live loop reads while the UI reports that restore failed.

This requires an injected LittleFS open/write/short-write failure test because ordinary happy-path restore tests will not exercise it. Every failure after the live registry becomes validation scratch must use one cleanup/rollback exit, and physical outputs should be re-parked before normal service resumes.

### OT-AUD-003 — open AP and unauthenticated mutating APIs

The AP password is optional and an empty value creates an open network (`src/system/web/WebServer.cpp:954-970`). No HTTP authentication, authorization, request origin, CSRF token, or equivalent server-side access check was found around the route registration. Mutating endpoints include START/limited START, general commands, config and hardware writes, factory reset/restore, asset replacement, log deletion, and firmware OTA.

The server does enforce operating-state and hardware preconditions, which is positive, but it assumes that an associated network client is trusted. A direct API client can sequentially enable Developer Mode and Bench Mode in STANDBY; Bench Mode bypasses safety/feedback checks. Dashboard confirmation dialogs are client-side UX and do not authenticate direct requests.

The dedicated `/api/start` endpoint accepts an empty POST body (`src/system/web/WebServer.cpp:2033-2051`). Because no Origin/Referer/Sec-Fetch validation or CSRF token exists anywhere in the server, an ordinary cross-origin HTML form can attempt this state-changing request without needing to read the response. Browser private-network/mixed-content policy varies and may block some contexts, so this is a browser-dependent attack path rather than a universal exploit; it nevertheless means an AP password alone does not protect an already-associated operator browser from cross-site request forgery.

Minimum tester rule if code cannot be changed in time: every ECU must be provisioned with a unique, strong AP password before fuel, ignition, starter, or throttle outputs are connected; the ECU browser/device should not browse unrelated content while associated. The tester guide must state that the Wi-Fi network and connected client are part of the safety boundary and must not be shared. A server-side authenticated maintenance/session mechanism with per-session CSRF protection is the stronger control.

### OT-AUD-004 — registry STOP loss fails open

The official S3 profile assigns STOP to a TCA9554 registry input (`pcb_profiles/official/openturbine-ecu-s3-v1.otpcb.json:206`). `registryControlInput()` returns false when that channel is unhealthy (`src/main.cpp:2964-2977`), and `checkStopSwitch()` consequently treats loss as inactive (`src/main.cpp:2980-3013`).

The runtime fail-closed registry roles in `checkGeneralDI()` include `fault`, `estop`, conditionally `low_oil_switch`, and conditionally `oil_zero_switch`, but not `stop_switch` (`src/main.cpp:1603-1608`). Runtime expected-device handling faults unavailable engine-affecting I2C outputs, not the STOP input. Therefore a TCA9554 or bus failure during STARTUP/RUNNING can remove the software STOP path without causing shutdown.

Regardless of a software correction, turbine operation should retain an independently wired, fail-safe removal of fuel and/or ECU power that does not depend on the MCU, I2C bus, expander, Wi-Fi, or application loop.

### OT-AUD-006/007 — update authenticity is not established

The ECU `/update` endpoint verifies the ESP update format/write operation but does not validate an OpenTurbine product identifier, expected version/build, cryptographic signature, or approved image digest (`src/system/web/WebServer.cpp:2314` onward).

The public `OpenTurbine-Setup-v0.6.2-windows-amd64.exe` has Authenticode status `NotSigned`; its SHA-256 does match the published release checksum. Release signing is conditional on a secret being present, while `docs/SETUP_TOOL.md:160` says public release workflow signing is required. The Setup Tool obtains a package checksum from `usedURL + ".sha256"` (`tools/setup_tool/main.go:2169`, verification near line 2249), so the hash catches accidental corruption but is not an independent authenticity proof if the same origin is compromised.

The executable later launches `tools/esptool.exe` from that separately downloaded package. The public v2.0.1 helper is also Authenticode `NotSigned` (SHA-256 `f25ea3560a67a18fbfeccf00d4ad32d7a792f6172aa929930a9128dd20a525bc`), so signing only the Setup Tool EXE would not authenticate the code it delegates clean USB erase/flash operations to. `findEsptool()` also prefers an `esptool.exe` or `tools/esptool.exe` beside the GUI over the package copy and performs no digest/signature check (`tools/setup_tool/main.go:2782-2807`). By contrast, every inspected `.cat`, `.sys`, and driver DLL in the public CP210x/WCH folders currently has a valid Microsoft Windows Hardware Compatibility Publisher signature. The release trust design should cover the package manifest/helper executable as well as the GUI executable, and the tool should verify that independent trust before launching the helper.

Offline fallback does not preserve the original outer-package verification either. Cached ZIPs are reopened and accepted from the per-user work directory using only their internal schema/content checks; if GitHub download fails, that cached package is used without rechecking a stored trusted outer SHA-256 (`tools/setup_tool/main.go:2080-2117` and `tools/setup_tool/main.go:2155-2163`). Adjacent local packages are likewise intentionally trusted as development overrides. Record the independently authenticated digest/signature with the cache and revalidate it on every use; make local-override mode explicit and visibly distinct from the recommended release channel.

### OT-AUD-022 — setup package extraction is unbounded

The package downloader streams the response to disk through `copyWithProgress()` with a four-minute timeout but without rejecting an excessive `Content-Length` or limiting bytes when the length is absent or false (`tools/setup_tool/main.go:2277-2318`). `unzip()` rejects absolute and parent-relative paths, but iterates every entry and copies its entire expanded content without a file-count, per-entry, or total-expanded-byte ceiling (`tools/setup_tool/main.go:2473-2512`). The same helper is used for both the complete setup archive and nested dashboard ZIPs.

This does not bypass the existing checksum/trust boundary and is therefore classified as an availability/resource-exhaustion issue, not code execution. A malicious or accidentally malformed selected/downloaded package can consume temporary-disk space and keep extraction busy. The nested-dashboard path also creates a separate `openturbine_assets_*` temporary root but never records or removes it after successful verification or failure (`tools/setup_tool/main.go:3612-3631`); `Package.cleanup()` only owns the outer `openturbine_setup_pkg_*` root. Enforce limits before extraction using ZIP metadata and again while copying so forged metadata cannot bypass the ceiling, and give every nested temporary root a deterministic cleanup owner.

### OT-AUD-023 — two important Hardware fields lack accessible names

An independent rendered-DOM pass at a 350-pixel viewport checked every dashboard page for visible, enabled form controls without a wrapping label, matching `label[for]`, `aria-label`, or `aria-labelledby`. All pages passed except two fields on Hardware: `f-profile-id` and `f-wifi-password`. Their visible captions are sibling `<span class="hw-label">` elements, not programmatically associated labels (`data_src/hardware.html:85-96`; the same markup is in `data_src/pages/hardware.shell.html:84-95`). Placeholders are not durable accessible names, especially because the password placeholder changes with saved state.

This is a focused accessibility/voice-control issue rather than a general form-label failure: the same pass found zero unlabeled visible fields on Dashboard, Config, Calibration, Sequence, Log, and Tools. Use real `<label for>` elements or stable caption IDs referenced by `aria-labelledby`, then add the check to the UI audit.

### OT-AUD-024 — dashboard update recovery does not prove one complete generation

ESP32-S3 stages the complete dashboard set and rolls the whole set back if a swap fails (`src/system/web/WebServer.cpp:2414-2442`). Classic cannot fit two complete generations in its 704 KiB filesystem, so `_installAssetRolling()` replaces one completed asset at a time and immediately deletes that file's backup (`src/system/web/WebServer.cpp:535-552`). If a later file is rejected, storage fills, or the client disconnects, the timeout cleanup removes only `.upload` files; already installed files remain from the new generation while untouched files remain old.

The prior HIL audit explicitly tested this recovery model and confirmed Tools/API access plus a successful complete retry (`docs/internal/VERIFICATION_AUDIT_2026-07-30.md:85-103`). The Setup Tool also verifies all assets after a nominal complete update, and `tools.html` is last so the retry surface ordinarily survives. Those are useful mitigations, but they do not prevent a user from operating the mixed firmware/UI state after an error or interrupted manual update. A persistent generation/complete-set marker should inhibit START and show a recovery-only page until all assets from one build are installed; alternatively use two selectable asset slots or an archive format that can be atomically selected after streaming validation.

The S3 has enough storage to stage a complete set and its normal power-loss classification is internally coherent: backup plus remaining upload files means roll back, while backup files without remaining uploads means every replacement was installed. However, every `remove()` and `rename()` in the S3 rollback, reboot-time recovery, and cleanup paths is unchecked (`src/system/web/WebServer.cpp:516-522`, `src/system/web/WebServer.cpp:558-584`, `src/system/web/WebServer.cpp:2428-2442`). This matters specifically because those paths run after a filesystem operation has already failed. A failed rollback can therefore leave missing or mixed pages without setting a persistent maintenance fault or inhibiting START. Treat S3 as normally set-atomic, not failure-atomically proven: verify every rollback postcondition and retain a recovery-only state until one complete generation is demonstrably present.

### OT-AUD-025 — third-party redistribution needs explicit clearance

The public package contains the current CP210x Universal Windows Driver 11.5.0 and its `SLAB_License_Agreement_VCP_Windows.txt`. That bundled agreement says redistribution is allowed only with modified INF/XML files and separately requires downstream recipients to accept an end-user agreement at least as protective as Silicon Labs' terms (sections 3(e) and 4(g)). OpenTurbine's documentation instead requires complete **unmodified** vendor-signed packages (`docs/SETUP_TOOL.md:22,82-86`), and the Setup Tool invokes `pnputil` after a driver button click without displaying or obtaining acceptance of the packaged agreement (`tools/setup_tool/main.go:1588-1613,2649-2674`). Modifying the INF would also invalidate the currently valid Microsoft catalog signature unless the driver were recertified; Silicon Labs' own customization guidance warns about that consequence.

The WCH payload contains no license/EULA/notice file in the published archive. WCH's official CH341 download page does describe its installer as usable for distribution with a product, but that short product-page statement is not a substitute for recording the applicable redistribution terms and required notices for the exact CH341/CH343 payloads.

The same release ZIP distributes a standalone `tools/esptool.exe` but contains no esptool `LICENSE`, copyright notice, corresponding-source archive, or written source offer, and the OpenTurbine documentation has no such notice. Espressif's official project identifies esptool as GPL-2.0-or-later. The precise compliance steps depend on how this executable was built and conveyed, but shipping the binary with no GPL text/source path is at minimum an unresolved distribution gap. Record the exact esptool version/source commit and build recipe, include the applicable license/notices, and provide the corresponding source in the form required for the chosen distribution method.

The package also omits OpenTurbine's own `LICENSE` even though the repository MIT text requires the copyright/permission notice to accompany copies or substantial portions. Firmware dependencies include LGPL-3.0 components (`AsyncTCP` and `ESPAsyncWebServer`) and other separately licensed libraries, but the release bundle has no consolidated third-party notices, license inventory, source/relink information, or SBOM. Add a reproducible license/SBOM stage to release CI and have the complete binary-distribution obligations reviewed, rather than fixing only the two immediately visible files.

This report does not make a legal determination. It identifies an unresolved, artifact-specific release condition: do not send the current third-party bundle to testers until the rights/acceptance and open-source compliance paths are confirmed. Safer driver options may be to direct users to vendor/Windows Update downloads, use a vendor-provided redistributable installer that presents its own terms, or obtain explicit permission for this packaging flow. Relevant primary sources: [Silicon Labs CP210x VCP downloads](https://www.silabs.com/software-and-tools/usb-to-uart-bridge-vcp-drivers), [Silicon Labs driver customization guidance](https://www.silabs.com/documents/public/application-notes/an220-usb-driver-customization.pdf), [WCH CH341SER download](https://www.wch-ic.com/downloads/ch341ser_zip.html), and [Espressif esptool repository/license](https://github.com/espressif/esptool).

### OT-AUD-026 — elevated driver helper accepts unauthenticated paths

When invoked with `--install-inf-driver`, the Setup Tool enters its elevated helper before opening the GUI (`tools/setup_tool/main.go:273-276`). That mode accepts `--driver-root`, `--result`, and `--log` directly from its command line, checks only that the root contains at least one INF, calls elevated `pnputil` over every INF below that arbitrary root, then creates/truncates the caller-selected result and log paths (`tools/setup_tool/main.go:2572-2627,2649-2674`). It does not verify a one-time parent-generated nonce/request file, constrain the driver root to the extracted OpenTurbine package, or constrain outputs to the Setup Tool log directory.

Windows still presents UAC and `pnputil` normally enforces driver-signing policy, so this is not a silent privilege escalation. It is nevertheless a signed-binary/confused-deputy risk: another local process can present an OpenTurbine elevation prompt while asking the trusted helper to install unrelated signed INFs and write/truncate diagnostic files at elevated paths. Pass a restrictive request file created in a user-only directory with a random nonce, validate its owner/ACL and single use, canonicalize every path, require the driver root to be under the exact verified package root, and require result/log paths under the intended per-user log root.

### OT-AUD-027 — destructive USB flash plan is under-validated

`flashUSB()` checks that each address is hexadecimal and not duplicated and that each referenced file exists. A SHA-256 is checked only when the optional manifest field is nonempty (`tools/setup_tool/main.go:3344-3384`); the published manifest supplies no SHA-256 for any USB flash entry. It does not parse addresses to integers, reject overlapping `[address,address+size)` ranges, ensure segments fit the detected chip's declared flash size, require the exact bootloader/partition/app/filesystem set, constrain relative/absolute file paths to the verified package, or compare addresses with the target partition table. It then erases the entire board before esptool gets the opportunity to reject a bad plan.

The v2.0.1 manifest currently uses the expected canonical addresses and its outer ZIP checksum matched, so this is not evidence that the published images overlap. It is a pre-erase validation gap: a packaging regression, locally supplied package, altered cache, or compromised same-origin package can turn a clean install into an avoidable erased/non-booting board. Build a typed per-target flash plan, require hashes and sizes for every entry, enforce known flash bounds and non-overlap, verify partition-table/layout consistency, prohibit absolute/out-of-root paths, and only issue `erase_flash` after all checks pass.

### OT-AUD-028 — non-web START paths omit the all-output-idle gate

The web/API START preflight calls the canonical `OutputActivity::anyPhysicalDemand(true)` check and refuses to start when any fitted physical output is active, except the explicitly allowed automatic standby oil-feed floor (`src/system/web/WebServer.cpp:408-409` and `src/system/web/WebServer.cpp:472-476`). `OutputActivity` covers both core actuator demands and generic registry-output demands (`src/system/OutputActivity.h:10-48`).

The authoritative ECU-core handler used by the physical START switch and cluster serial does not call that gate. It checks `extraCooldownActive` and timer bookkeeping through `anyToolTimerActive()` (`src/main.cpp:2413-2433`), but timer bookkeeping is not equivalent to current physical demand. In particular, manual `SET_OIL_PCT` persists in `_manualOilPct` without a timer (`src/main.cpp:1250-1253` and `src/main.cpp:2661-2669`), and Control Rules can assert core or registry demands independently of every Tools timer. Physical START queues `OTCommand::START` directly (`src/main.cpp:3062-3067`), and cluster serial does the same (`src/system/ClusterSerial.cpp:720-726`), so both reach the weaker handler.

A configured nonzero generic registry `safe_demand` is another reproducible source. Registry initialization copies that value into `registryOutputDemand` and writes it physically (`src/Hardware.h:964-990`); at boot there is no call to `enterStandby()` to replace it with zero. The Hardware UI explicitly permits an On/nonzero power-on state (`data_src/pages/hardware-registry-catalog.js:468-481`). Web START will therefore remain blocked by design while the weaker physical/cluster path can proceed. The fix needs an explicit policy for such intentionally safe-position outputs rather than merely changing timer checks.

This was checked against adjacent maintenance gates: the core handler independently rejects an OTA/maintenance upload and a scheduled reboot (`src/main.cpp:2318-2337`), so those related asymmetries are already closed. The remaining mismatch is specifically the physical-output-idle invariant. It compounds OT-AUD-016/018 because a rule-energized output that blocks web START can remain energized while a physical or cluster START transitions to STARTUP. Put the canonical demand check at the final ECU-core START transition so every producer shares it, and test web, physical, and cluster START against each persistent, timed, rule-owned, and registry-owned output source.

### OT-AUD-029 — web configuration writes expose partial state to the live ECU loop

The full-config restore marks a maintenance upload, which correctly blocks queued commands, but it never claims `ConfigApplyGate` and does not quiesce the ECU loop (`src/system/web/WebServer.cpp:3057-3088`). It then passes the live `HardwareConfig::channelRegistry` as validation workspace. `HardwareConfig::validateJson()` calls `ChannelRegistry::fromJson()` on that object; `fromJson()` first clears it and then rebuilds counts/entries incrementally (`src/system/web/WebServer.cpp:3140-3148`, `src/system/HardwareConfig.cpp:3153-3173`, and `src/system/ChannelRegistry.h:343-346`). Core 1 concurrently traverses the same registry for START/STOP/general inputs, Rules, sensor updates, and actuator updates on every loop.

After validation, restore applies the uploaded hardware statics and settings/rules directly on the web core before it atomically writes the file and schedules reboot (`src/system/web/WebServer.cpp:3170-3173` and `src/system/web/WebServer.cpp:3209-3258`). During that interval, Core 1 keeps using the already-initialized physical sensor/actuator objects together with the newly replaced flags, pins, registry, dependencies, and rules. The maintenance flag does not suppress `Hardware::updateSensors()`, `RulesEngine::evaluate()`, or `Hardware::updateActuators()` (`src/main.cpp:3375-3422`). Thus the comment that idle STANDBY makes the live registry safe scratch is not a synchronization guarantee; OT-AUD-016/018 also show that STANDBY does not imply demands remain zero on later ticks.

This finding is separate from OT-AUD-021: OT-AUD-021 is a specific failure branch that forgets to restore the previous live registry, while OT-AUD-029 exists during successful and most rejected restores even when rollback eventually runs. Keep validation objects isolated from authoritative runtime state. Prefer validating and atomically storing the uploaded document without applying it at all, then let the normal reboot load be the sole publication point. If runtime application is unavoidable, make Core 1 enter an explicit all-off/quiescent state and own the complete copy under one transaction boundary; a command-only maintenance flag is insufficient.

The same architectural race is present in the ordinary hardware POST/PATCH paths. They claim `ConfigApplyGate`, but that gate serializes web writers, the final START transition, and the later Core-1 apply; it does not stop the current control iteration from reading `HardwareConfig` while `HardwareConfig::fromJson()` replaces the live registry and other statics on Core 0 (`src/system/web/WebServer.cpp:2795-2824` and `src/system/web/WebServer.cpp:3018-3037`; `src/system/ConfigApplyGate.h`). The finding is therefore not limited to the restore endpoint. Full restore is the clearest/highest-risk instance because it omits the gate entirely and also installs uploaded rules/settings before reboot.

### OT-AUD-030 — reset recovery is marked safe before outputs are safe

`ResetRecovery::markActive()` records STARTUP/RUNNING activity in RTC memory, and an abnormal watchdog/panic/brownout reset only arms the operator-acknowledged recovery lockout when that retained marker still says active (`src/platform/esp32/PlatformInit.h:9-15` and `src/platform/esp32/PlatformInit.h:94-121`). `enterStandby()` clears the marker near the beginning of the transition, before it sets `mode = STANDBY`, zeros every demand/timer, and calls the physical `Hardware::allOff()` boundary (`src/main.cpp:2100-2186`).

Active sequence `onExit()` callbacks usually clear their logical demands before this point, but the corresponding physical writes occur later; `Hardware::allOff()` is the explicit immediate physical-off operation (`src/Hardware.h:2542-2588`). A panic/watchdog/brownout between line 2109 and line 2185 can therefore reboot with the retained marker already safe even though the transition has not proved every output off. This is a narrow timing window, not evidence of a routinely energized reboot, but it negates the recovery interlock precisely in the reset case it exists to handle. Clear the retained active marker only after `Hardware::allOff()` completes and the safe mode/demands have been published. Fault-injection tests should reset after each transition operation and require lockout until that final point.

### OT-AUD-031 — automatic relight limits and confirmation are incomplete

Automatic relight keeps fuel open and the selected ignition output active while RUNNING (`src/main.cpp:1327-1330`). Its only attempt-duration bound is conditional: `relight_timeout_ms = 0` explicitly disables timeout in `SafetyMonitor` (`src/engine/SafetyMonitor.h:294-311`). Zero is accepted by firmware validation and normalization and is offered by the UI as “no timeout” (`src/system/Config.cpp:735-743`, `src/system/ConfigSerialize.cpp:731-736`, and `data_src/config.html:237-245`). The sequence validator emits only a warning that this can leave ignition active indefinitely (`src/main.cpp:1122-1125`). With healthy N1 remaining above the effective minimum and no confirmation, the ECU therefore stays RUNNING with fuel and relight ignition indefinitely instead of faulting to shutdown.

There is also no configurable or enforced attempt count. `relightAttempts` is telemetry only: it increments when the callback starts and resets on RUNNING/STANDBY entry; no code compares it with a limit (`src/engine/EngineData.h:236-237`, `src/main.cpp:1983-1994`, `src/main.cpp:3284-3296`). Yet the dashboard says it shows attempts “vs the configured limit,” and the user guide instructs the operator to configure an attempt count (`data_src/index.html:478` and `docs/USER_GUIDE.md:375-383`). Repeated loss/recovery cycles in one run can therefore cause unbounded new relight attempts despite the guide's explicit fuel-accumulation warning.

Finally, N1 confirmation does not prove recovery. After a fixed one-second dwell it returns true whenever N1 is already at or above `relightConfirmRpm` (`src/main.cpp:1342-1350`); no below-to-above crossing or positive change from the relight baseline is required. A flame- or EGT-triggered flameout while N1 remains above that threshold cuts the igniter and logs “Relight successful” after one second even if the original combustion-loss signal remains asserted. `SafetyMonitor` will eventually fault when its separate timeout expires, but the premature confirmation can remove ignition during the intended recovery window and makes the event log misleading.

Make a finite timeout and finite per-run attempt ceiling mandatory when automatic relight is enabled. For N1 confirmation, capture the trigger baseline and require a defensible rise/crossing (or restrict N1 confirmation to an N1-triggered event with explicit hysteresis). Keep one authoritative relight state so ignition, SafetyMonitor timing, telemetry, and success logging cannot disagree. Add executable cases for loss sources × confirmation sources, N1 initially below/at/above the confirmation threshold, intermittent recovery, timeout zero/imported legacy values, and attempt-limit exhaustion.

### OT-AUD-032 — configurable STARTUP waits can hold hazardous outputs forever

The sequence editor permits `WaitForInput` in STARTUP with a timeout from 0 to 60 seconds; zero is the default and explicitly means wait forever (`data_src/pages/sequence-definitions.js:439-457`). Firmware implements that literally: the block returns `Running` indefinitely when the expected DI state never arrives and `timeoutMs == 0` (`src/engine/sequencer/blocks/WaitForInput.h:34-58`). Validation checks only that the selected DI exists; it does not require a finite timeout or consider what earlier blocks have energized (`src/main.cpp:680-685`). There is no independent whole-STARTUP deadline around `g_sequencer.tick()`.

Because the editor allows arbitrary order, `PreIgnSpark` and `FuelOpen` can precede the infinite wait. Those blocks deliberately leave the igniter and fuel solenoid on for later blocks (`src/engine/sequencer/blocks/PreIgnSpark.h` and `src/engine/sequencer/blocks/FuelOpen.h`). `FlameConfirm` provides a bounded no-light abort only if the sequence reaches it. A valid saved sequence such as `PreIgnSpark → FuelOpen → WaitForInput(timeout=0) → FlameConfirm` therefore remains in STARTUP indefinitely with fuel and ignition commanded if the external input never changes. General safety checks still run, but they are not a no-ignition fuel-accumulation timer and do not make this ordering safe.

Custom while-style blocks have the same zero-means-unbounded execution rule (`src/main.cpp:131-165`) and can combine entry/step/exit actuator actions, so the invariant should be systemic rather than special-casing one named block. Require every STARTUP wait after any hazardous action to have a conservative finite timeout, or enforce a separate maximum time from first fuel/ignition/starter enable to confirmed flame/abort. The sequence validator should reject rather than merely warn on unbounded hazardous paths. Add graph/path tests covering every action that can energize fuel, ignition, starter, glow/wet fuel, and generic registry outputs before each wait/while block.

Imported configuration can create another unbounded built-in block: firmware's generic millisecond-field validator accepts zero for `safety_hold_timeout_ms`, while `SafetyHold` only faults when that value is greater than zero (`src/system/Config.cpp:582-589` and `src/engine/sequencer/blocks/SafetyHold.h:75-84`). The ordinary editor's minimum is 100 ms, so this path mainly concerns restore/legacy/manual JSON and further supports enforcing the invariant in firmware rather than only in the UI.

### OT-AUD-033 — default native safety-switch wiring fails open on a broken wire

The registry safety path says that configured `fault`, `estop`, low-oil, and zero-oil inputs fail closed when disconnected or stale (`src/main.cpp:1594-1608`), and an unhealthy operating input does trigger a fault (`src/main.cpp:1617-1633`). That guarantee is real for an I2C device/bus that becomes unavailable, because the device manager can return unhealthy. It is not real for a direct GPIO switch circuit: every installed native digital registry input is marked healthy unconditionally after `digitalRead()` (`src/Hardware.h:845-848`). The separate legacy DI path likewise stores only a Boolean level and has no health/wire-break state (`src/main.cpp:1492-1512` and `src/main.cpp:3247-3264`).

The dashboard's generated registry defaults make safety switch roles active-low with the internal pull-up enabled, and the user guide describes active-low/pull-up as the registry-driven default (`docs/USER_GUIDE.md:311`). With that common switch-to-ground arrangement, a broken or unplugged wire is pulled high and is interpreted as inactive, not as a safety trip. Configuration validation permits either polarity and pull choice and checks only that pull-up and pull-down are not simultaneously enabled (`src/system/ChannelRegistry.h:512-523`); it does not warn that the default is not line supervised. The same electrical limitation exists downstream of a still-healthy TCA9554 input: loss of the whole device trips, but an open switch wire can remain a valid inactive level.

This is not something software can solve from one unsupervised Boolean GPIO alone. For tester hardware, safety interlocks and the independent emergency fuel/power stop should use deliberately fail-safe normally-closed or end-of-line-supervised circuits whose open-wire state is distinguishable and asserted. The UI should label the active-low/pull-up default as noise-resistant rather than wire-break-safe, validation should warn on safety roles without a supervised/fail-safe topology, and the guide/runtime messages must distinguish device/bus loss from field-wire continuity. Add simulation truth tables for switch open/closed, ground/3.3 V short, device loss, boot, and RUNNING for every safety role and supported adapter.

### OT-AUD-034 — EGT-only flameout/pullback feedback loss does not latch reduced power

The shared feedback model correctly classifies EGT as operationally required when overtemperature, hot-start, EGT-sourced flameout, or EGT pullback consumes it (`src/system/FeedbackRequirements.h:84-89`). Its RUNNING failure mask also flags unhealthy or stale primary EGT for any of those configured uses (`src/system/FeedbackRequirements.h:218-227`). `ThrottleSlew` uses that same broad predicate to freeze further fuel increases immediately when EGT becomes unhealthy (`src/engine/controllers/ThrottleSlew.h:81-99`).

The persistent feedback-loss latch is narrower. `SafetyMonitor` enters Reduced-Power Mode for unhealthy EGT only when `safetyOvertemp` is enabled (`src/engine/SafetyMonitor.h:449-477`). It does not use `egtForProtectionOrControl()` there and has no equivalent branch for EGT-sourced flameout or enabled EGT pullback. Meanwhile, EGT flameout detection explicitly returns "not lost" when primary EGT is unhealthy (`src/engine/SafetyMonitor.h:652-667`), and the EGT pullback applies only while that reading is healthy (`src/engine/controllers/ThrottleSlew.h:167-174`). Therefore a permitted configuration with overtemperature disabled but EGT flameout and/or EGT pullback enabled can lose EGT in RUNNING, silently lose both protections, freeze only upward slew, and continue indefinitely at the current fuel demand without the intended persistent reduced-power cap or warning state.

This is narrower than total loss of fuel control: the immediate no-increase interlock remains effective, and the issue is masked when overtemperature is also enabled. The fix should derive `protectionBlind` from the same authoritative `protectionFailureMask()`/requirement predicates used by START and throttle enforcement, while excluding only explicitly start-only uses such as hot-start protection. Add executable cases with each EGT consumer enabled alone and in combination, healthy-to-unhealthy and stale transitions at low/mid/high demand, plus restoration behavior; no operational protection should disappear merely because an unrelated EGT protection is disabled.

### OT-AUD-035 — imported settings can reduce the shutdown safety waits to zero

The Sequence editor constrains RPM-drop and final-stop timeouts to at least 1,000 ms and cooldown to at least 10,000 ms (`data_src/pages/sequence-definitions.js:350-371` and `data_src/pages/sequence-definitions.js:401`). Firmware validation is weaker: all shutdown millisecond fields share a generic validator whose accepted range starts at zero (`src/system/Config.cpp:537-540` and `src/system/Config.cpp:626-635`). Normalization also preserves zero for all three values (`src/system/ConfigSerialize.cpp:723-725`), and `Hardware::applyConfig()` copies them unchanged into the live shutdown blocks (`src/Hardware.h:1227-1237`). A restore, direct API client, or manually authored file can therefore create settings the normal editor does not offer.

The resulting behavior defeats three distinct mechanical protections. `RPMDrop` advances as soon as elapsed time is greater than a zero timeout, even with high or unhealthy N1, allowing a following starter-assisted cooldown to engage against a still-windmilling shaft (`src/engine/sequencer/blocks/RPMDrop.h:20-29`). `CooldownSpin` turns on its selected starter/oil/scavenge outputs and then completes on the next tick when its zero timeout expires, immediately turning them back off (`src/engine/sequencer/blocks/CooldownSpin.h:24-50` and `src/engine/sequencer/blocks/CooldownSpin.h:88-101`). `FinalStop` similarly treats its zero timeout as proof enough to cut the main oil pump without a healthy low-RPM confirmation (`src/engine/sequencer/blocks/FinalStop.h:22-46`). A structurally valid sequence still passes the non-empty shutdown gate, so this is not blocked by the existing structural error check.

The firmware must enforce the safety-critical minima independently of HTML controls, ideally with engine/profile-specific conservative bounds and an explicit migration error instead of silent clamping. Add restore and settings-API tests at -1, 0, minimum-1, minimum, maximum, and maximum+1, then simulate high/low/unhealthy N1 and hot/healthy/unhealthy EGT through the complete shutdown sequence. Until fixed, inspect the exact candidate/tester configuration JSON and reject any zero or sub-policy shutdown timeout before flashing.

### OT-AUD-036 — automatic feedback-loss reduced power does not inhibit the afterburner

There are two ways the ECU reaches reduced power. A limited START sets both `limpOverrideSensor` and `limpMode` (`src/main.cpp:2569-2572`). A sensor that fails during an ordinary run instead causes `SafetyMonitor` to set only `limpMode = true`; it does not populate an override identity (`src/engine/SafetyMonitor.h:449-483`). That distinction is legitimate for diagnosis, but the afterburner interlock uses the identity rather than the effective safety state.

The web preflight rejects AB FIRE only when `limpOverrideSensor != NONE` (`src/system/web/WebServer.cpp:391-394`), the ECU-core command repeats that same predicate (`src/main.cpp:2799-2809`), and automatic throttle/switch/analog AB triggering plus shutdown of an active AB is gated by the same identity (`src/main.cpp:1819-1864`). Thus a mid-run feedback loss can visibly latch reduced power while allowing manual AB ignition, automatic AB ignition on a new trigger edge, or continued operation of an already-lit afterburner. The final main-fuel actuator does cap the composed main throttle plus AB offset when `limpMode` is true (`src/Hardware.h:2358-2369`), but the separate AB valve and AB pump are still written from their independent demands (`src/Hardware.h:2396-2398` and `src/Hardware.h:2499-2500`). The reduced-power cap therefore does not bound total combustion/fuel authority.

The dashboard contract says reduced-power operation disables the afterburner (`data_src/index.html:122` and `data_src/app.js:746-761`), although the banner is itself shown only for the limited-start identity and fails to disclose an automatically latched mid-run state consistently. Use one effective reduced-power predicate for UI, manual API validation, physical/registry trigger handling, active-AB shutdown, and final output arbitration. Test every feedback source failing before AB fire, during ignition, and while AB is running, with manual/throttle/switch/analog triggers and with operator-requested limp. This compounds OT-AUD-001: even before another path clears the automatic limp Boolean, AB authority is still available.

### OT-AUD-037 — subsequent feedback losses do not escalate after automatic reduced power latches

The multiple-failure shutdown path runs only when a limited START has populated `limpOverrideSensor`; it compares the current required failure mask with that one explicitly overridden sensor and faults on any additional bit (`src/engine/SafetyMonitor.h:427-447`). An ordinary mid-run sensor loss does not populate that field. Instead, after 500 ms the separate feedback-blind branch sets only `limpMode = true` (`src/engine/SafetyMonitor.h:449-483`).

Those branches then exclude all later escalation. On subsequent checks, the limited-start branch is skipped because `limpOverrideSensor == NONE`, and the ordinary branch is skipped because it is conditioned on `!ed.limpMode`; its timer is reset in the `else` path (`src/engine/SafetyMonitor.h:431-485`). There is no automatic failed-sensor mask or first-failure identity elsewhere in `EngineData`. Consequently, after N1, N2, EGT, oil, fuel-pressure, battery, pressure, torque, flame, oil-loop, or monitored-output feedback first latches reduced power, any number of other required feedback channels can become unhealthy without a `MULTIPLE_SENSOR_FAILURE` or equivalent shutdown.

Individual hard trips also require healthy data before comparing a limit—for example overtemperature, oil pressure, fuel pressure, and battery voltage (`src/engine/SafetyMonitor.h:248-276` and `src/engine/SafetyMonitor.h:324-350`)—so they cannot compensate once their own sensors are among the later failures. `ThrottleSlew` continues to block further fuel increases for failed non-overridden feedback (`src/engine/controllers/ThrottleSlew.h:81-99`), which limits but does not remove existing fuel demand or prove continued safe operation. At a high steady demand, the ECU can therefore remain RUNNING while progressively losing the protections that justified continued reduced-power operation.

Treat this as a release blocker unless a documented, justified policy explicitly allows an identified set of simultaneous blind protections. Track the authoritative current failure bitmask continuously, preserve the first automatic failure identity separately from manual limp demand, and enter fault shutdown when a second operationally required feedback source fails (or immediately for sources that must never be degraded). Add pairwise and three-way failure permutations for every feedback bit, both failure orders, transient recovery, stale-versus-unhealthy states, and failures during active AB/governor/oil-loop operation. This is related to OT-AUD-001 but persists even if manual controls can no longer clear the automatic latch.

### OT-AUD-038 — shutdown Abort handling can loop or hang indefinitely

The same `SequenceEngine` instance and callbacks run both startup and shutdown (`src/engine/sequencer/SequenceEngine.h:24-34`). Any block returning `Abort` calls the one `_abort` callback without passing the active sequence/mode (`src/engine/sequencer/SequenceEngine.h:106-125`). That callback is `enterAbortStandby()`, which is written entirely as a startup-abort handler: when `fuelEverOpened` is true it sets SHUTDOWN and starts the shutdown sequence again from block zero (`src/main.cpp:2190-2238`). It does not detect that the abort already occurred inside SHUTDOWN.

This is reachable from the ordinary editor. `WaitForInput` and `WaitForInputOff` are explicitly offered as shutdown blocks (`data_src/pages/sequence-definitions.js:762-770`). With a finite timeout, the block returns `Abort` if the requested input state is not reached (`src/engine/sequencer/blocks/WaitForInput.h:34-58`), so a sequence such as `ImmediateCut -> OilPumpOn -> WaitForInputOff(5 s) -> FinalStop` repeatedly restarts after five seconds and never reaches final all-off/STANDBY. The restart cuts combustion/starter momentarily but can immediately replay earlier starter, oil, fan, scavenge, valve, or side actions. With the UI's default zero timeout, the same block returns `Running` forever instead, continuously retaining demands established by preceding blocks. Validation checks only that the selected DI exists (`src/main.cpp:875-879`); it neither prohibits the unbounded shutdown wait nor gives Abort a shutdown-specific terminal policy.

Shutdown must have a deterministic, bounded safe terminal path. On a block Abort or Fault while already in SHUTDOWN, stop the sequence, synchronously cut hazardous outputs, apply the chosen oil/spindown emergency policy, and transition to a visible fault/lockout state without recursively replaying the same sequence. Require a finite timeout for all shutdown waits, and define whether timeout means continue, emergency-finalize, or lock out; it must not call a startup callback. Test every abort-capable/custom block in STARTUP and SHUTDOWN, with fuel-used true/false, timeout zero/nonzero, and hazardous enter/exit side actions before and on the failing block.

### OT-AUD-039 — afterburner confirmation is presence-checked, not order-checked

The custom afterburner editor allows arbitrary ordering of `ABCheckReady`, fuel valve/pump actions, ignition, `ABFlameConfirm`, and `ABStabilize` (`data_src/pages/sequence-definitions.js:775-783`). Firmware validation loops over the selected blocks and requires only that an `ABFlameConfirm` name appears somewhere; stabilization is optional and there is no relative-order or path check (`src/main.cpp:944-959`). The final completion callback repeats the same presence-only scan before accepting the sequence (`src/main.cpp:1721-1753`).

That permits confirmation with no causal relationship to the light-off being accepted. In timed-assumption mode, `ABFlameConfirm` completes after its delay regardless of fuel state (`src/engine/sequencer/blocks/ABFlameConfirm.h:111-118`), so `ABFlameConfirm -> ABSolOpen -> ABPumpOn` is accepted and enters AB Running without any post-fuel evidence. Sensor/EGT modes can likewise consume a stale/pre-existing condition before the new fuel action. Conversely, placing `ABStabilize` before confirmation sets `abMode = Running` in its `onExit()` (`src/engine/sequencer/blocks/ABStabilize.h:43-54`); the normal AB state logic can then begin applying main-fuel offset and AB pump demand while later custom blocks, including the nominal confirmation, are still running (`src/main.cpp:1881-1925`).

Validation must operate on ordered paths rather than token presence. At minimum, every path to AB Running should pass readiness (when configured), an actual ignition method, fuel admission, confirmation that starts after those actions, and only then stabilization/Running. Reject confirmation before the last causal fuel/ignition action and prohibit `ABStabilize` before confirmation. Capture per-attempt baselines at the correct boundary and make the sequencer, not an individual freely placeable block, own the transition to Running. Add permutation/property tests that generate all short custom AB orders and prove no fuel remains open and no Running state is reachable without a causally valid confirmation.

### OT-AUD-040 — firmware does not enforce sequence-specific block catalogs

The Sequence page intentionally exposes different allow-lists for startup, shutdown, afterburner ignition, and afterburner shutdown in `data_src/pages/sequence-definitions.js:747-783`. Firmware does not preserve that boundary. `HardwareConfig` reads every sequence name verbatim in `src/system/HardwareConfig.cpp:4152-4283`; `sanitizeSequenceBlocks()` removes blocks only when their fitted hardware is unavailable, not when the block belongs to another sequence context (`src/system/HardwareConfig.cpp:1096-1158`). `buildSequences()` then resolves every name through the same global block registry for all four sequencers (`src/main.cpp:337-411`). The name validator likewise checks only whether a name exists globally (`src/main.cpp:452-492`).

This can energize a main-engine actuator from an afterburner command using a full-config import that the browser editor itself cannot create. For example, an AB ignition list containing `StarterSpin` followed by `ABFlameConfirm` passes the current AB structural rule because that rule requires only the presence of `ABFlameConfirm` (`src/main.cpp:944-959`). When the AB is fired during RUNNING, `StarterSpin::onEnter()` asserts starter enable; because N1 is already normally above its light-off target, its first tick sets the configured starter demand, returns Complete, and deliberately leaves both commands asserted for the startup hand-off (`src/engine/sequencer/blocks/StarterSpin.h:24-34`, `src/engine/sequencer/blocks/StarterSpin.h:60-89`). No ordinary AB completion cleanup owns those main-starter commands. The same unrestricted global instances also make stateful blocks unsafe to share between the simultaneously running main-shutdown and AB-shutdown sequencers.

Treat the browser catalogs as part of the configuration schema and duplicate them as firmware-side per-context allow-lists. Reject, rather than silently strip, any wrong-context block during POST, restore, and boot validation. Add restore tests for every block/context pair and a concurrency test proving the main and AB sequencers can never tick the same stateful block instance.

### OT-AUD-041 — emergency STOP does not cancel older queued commands

`CommandQueue::pushEmergencyFront()` first tries to insert the emergency packet at the front and clears the queue only if that insertion fails because the queue is full (`src/system/CommandQueue.h:77-91`). This contradicts its own “supersede pending” contract: in the ordinary non-full case all older packets remain behind it. `CommandQueue::drain()` then consumes the entire queue in one ECU-loop pass (`src/system/CommandQueue.h:94-100`). Both the web STOP endpoint and cluster-serial STOP use this path, as do their AB_STOP equivalents (`src/system/web/WebServer.cpp:2053-2059`, `src/system/web/WebServer.cpp:2121-2123`, `src/system/ClusterSerial.cpp:721-729`).

The ordering creates a direct last-command inversion. If START has been queued while the ECU is in STANDBY and remote STOP arrives before the next Core-1 drain, the queue becomes `STOP, START`. STOP is a no-op in STANDBY (`src/main.cpp:2603-2609`); the next packet is then accepted by the normal START transition and starts the configured sequence in that same drain (`src/main.cpp:2341-2599`). The STOP endpoint can therefore return success even though an older command starts the engine immediately afterward. The identical pattern exists for `AB_FIRE, AB_STOP`: AB_STOP placed first is harmless while AB is Off, then the older AB_FIRE can start light-off. A physical STOP that remains asserted is separately rechecked and blocks START, but that does not protect a web/cluster STOP because those requests do not latch `stopSwitchActive`.

STOP must be a cancellation barrier, not merely a priority hint. Atomically discard or generation-invalidate every older command that can start or energize an output before enqueuing STOP; AB_STOP should at least invalidate older AB_FIRE commands. Consider retaining only idempotent de-energizing packets. Add executable permutation tests for START/STOP, START_LIMITED/STOP, every standby tool/STOP, and AB_FIRE/AB_STOP at queue depths 0, 1, 15, and 16, including producer races and commands arriving after (rather than before) the barrier.

### OT-AUD-042 — software “power-on state” does not cover the reset interval

The earliest generic-board initialization parks only the compile-time fuel-solenoid, primary-igniter, and starter-enable pins, and its source comment explicitly states that external pull-offs are still required during reset (`src/platform/esp32/PlatformInit.h:27-46`). The actual runtime/remapped topology is unavailable until LittleFS mounts and `HardwareConfig::load()` finishes. Only then does `driveBootSafeStates()` drive throttle/starter/pumps and other runtime-configured pins, with its own comment acknowledging that the real remapped pin was floating until this point (`src/main.cpp:3119-3145`, `src/Hardware.h:2058-2085`). Even a profiled board cannot use software to control GPIO during the chip's electrical reset interval; its earlier profile parking only reduces the post-reset firmware window.

The tester-facing contract does not communicate that limitation. The Hardware page labels `safe_demand` as **Power-on state/demand** and says it is written while the output is initialized (`data_src/pages/hardware-registry-catalog.js:468-481`). The wiring/pre-start guide tells users to set boot-safe demand deliberately but does not require an external pull-up/pull-down, driver inhibit, or power interlock for hazardous outputs (`docs/USER_GUIDE.md:102-120`, `docs/USER_GUIDE.md:306-325`). A software value therefore risks being interpreted as protection across reset, bootloader, brownout, and config-load time when the source explicitly says it is not.

For every fuel, ignition, starter, pump, valve, and ESC/servo command sent to testers, require an external resistor or hardware enable/power gate that forces the physical inactive state while the ESP pin is high-impedance. Rename the UI field to “post-boot initialization state” (or add an adjacent reset-interval warning), put the electrical requirement in the wiring checklist, and make reset/brownout/power-cycle output capture a mandatory HIL acceptance test. This finding is a verified integration/documentation defect; whether any specific attached driver actually glitches cannot be resolved without hardware.

### OT-AUD-043 — imported zero durations bypass three intentional safety holds

The browser editors impose nonzero lower bounds on three deliberate safety delays: OilPrime timeout is at least 500 ms, SafetyHold stable time and overall timeout are at least 100 ms, and the physical START+STOP cooldown-skip gesture must be held for at least 500 ms (`data_src/pages/sequence-definitions.js:50`, `data_src/pages/sequence-definitions.js:197-198`, `data_src/pages/config-schema.js:137`). Firmware-side document validation does not enforce those same contracts. All startup millisecond fields, including `oil_arm_timeout_ms`, `safety_hold_ms`, and `safety_hold_timeout_ms`, use the generic zero-inclusive validator (`src/system/Config.cpp:537-540`, `src/system/Config.cpp:582-589`), while `cooldown_skip_hold_ms` is explicitly accepted from zero through 60,000 (`src/system/Config.cpp:837-841`). Load normalization preserves zero for the cooldown hold (`src/system/ConfigSerialize.cpp:788-794`), and the generic field readers copy the startup values directly into live configuration.

The consequences are distinct and observable in control flow. When no oil-pressure sensor is fitted (or in Bench Mode), OilPrime completes as soon as `elapsed >= timeoutMs`; with zero it can finish on its first tick after commanding the pump, so the documented timed prelubrication gate is effectively absent (`src/engine/sequencer/blocks/OilPrime.h:40-61`). SafetyHold begins its stability timer on the first passing sample and completes when `stable >= holdMs`; a zero hold therefore treats one healthy sample as the required continuously stable interval. A zero overall timeout also changes the documented bounded fault gate into an unlimited wait because timeout enforcement is conditional on `timeoutMs > 0` (`src/engine/sequencer/blocks/SafetyHold.h:71-84`). Finally, `checkCooldownSkip()` transitions directly to STANDBY once both physical buttons have remained asserted for the configured hold; at zero, the second polling pass is enough to bypass the active cooldown regardless of selected EGT (`src/main.cpp:1949-1977`).

These are not merely unusual but supported “zero disables” semantics: each value is hidden behind a nonzero UI minimum and the UI descriptions promise a duration, continuous stability, or a long-press gesture. Enforce the same conservative minima in the firmware validator used by restore and direct API writes, reject rather than silently reinterpret out-of-policy values, and add boundary tests at -1, 0, minimum-1, minimum, and maximum+1. Runtime tests should prove a sensorless oil prime lasts the configured dwell, SafetyHold requires multiple samples spanning the full interval and always has a bounded failure path, and the cooldown override cannot trigger before its minimum hold.

### OT-AUD-044 — parallel sequencers corrupt shared progress and fault attribution

`SequenceEngine` is instantiated separately for the main engine and afterburner, but every instance publishes progress into the same `EngineData.currentBlock`, `seqBlockIdx`, `seqBlockTotal`, and `seqWaitReason` fields (`src/engine/EngineData.h:214-218`). Starting or entering a block overwrites the shared block name and counters, while every block's `setWaitReason()` writes the same global reason (`src/engine/sequencer/SequenceEngine.h:53-59`, `src/engine/sequencer/SequenceEngine.h:168-179`, `src/engine/sequencer/IBlock.h:26-33`). The ECU loop ticks the main sequencer and then the AB sequencer on every iteration (`src/main.cpp:3398-3402`), so an active AB block deterministically wins after both have ticked or advanced.

Concurrent operation is an ordinary shutdown path, not an exotic race: both normal and fault shutdown call `enterABShutdown()` before starting the main shutdown sequence (`src/main.cpp:2015-2043`, `src/main.cpp:2046-2084`). The main start initially overwrites the AB progress fields, but any subsequent AB block transition overwrites them again. The web dashboard and cluster status expose only that shared record (`src/system/web/WebServer.cpp:1191-1195`, `src/system/ClusterSerial.cpp:657-662`), so their block name, numerator/denominator, and wait text can combine two different sequences. More seriously, the main `enterAbortStandby()` and shutdown `sequenceFaulted()` callbacks read `ed.currentBlock` rather than receiving the block that actually returned Abort/Fault (`src/main.cpp:2190-2221`, `src/main.cpp:2253-2269`). If the AB sequencer most recently published its state, the event log, fault description, and operator guidance name the wrong block.

Create independent main and AB progress structures, include a sequence identity in telemetry/log records, and pass the actual block name/result into completion callbacks instead of consulting mutable global display state. Add a deterministic test that advances/faults each sequencer in both loop orders during simultaneous shutdown and verifies that main and AB progress, wait reasons, and fault attribution remain internally consistent.

### OT-AUD-045 — withdrawn: sensor-free and external-start completion is intentional

Firmware treats only an empty startup list and unknown/unavailable block names as structural errors. For a nonempty list, missing sustained fuel delivery, missing starter/spool action, absent oil-protection arming, and timed ignition without sensor confirmation are warnings rather than errors (`src/main.cpp:703-758`, `src/main.cpp:820-840`). The browser makes this explicit by offering a danger-styled **Save anyway** action after its sequence warnings (`data_src/pages/sequence-rules-save.js:690-699`). The START gate blocks structural errors and hardware errors, but intentionally does not block warning-only graphs (`src/main.cpp:2539-2549`). When the last block returns Complete, `sequenceComplete()` calls `enterRunning()` without imposing a stock sensor/evidence recipe (`src/main.cpp:1982-2012`, `src/main.cpp:2242-2250`).

A concrete accepted graph is `FuelOpen -> ThrottleSet`; a single `IgniterOn` or `StarterEnOn` sequence is also accepted and leaves that selected command asserted (`src/engine/sequencer/blocks/FuelOpen.h:5-18`, `src/engine/sequencer/blocks/MoreBlocks.h:91-110`, `src/engine/sequencer/blocks/ActuatorBlocks.h:7-18`, `src/engine/sequencer/blocks/ActuatorBlocks.h:37-42`). Those results can be deliberate for an externally spooled/ignited, sensor-free, or otherwise unusual installation. The User Guide expressly says the project supports varied layouts, that suggestions are not mandatory settings, and that warnings may be accepted unless an immediate unsafe operation, destructive data loss, or internally invalid configuration must be prevented (`docs/USER_GUIDE.md:5`, `docs/USER_GUIDE.md:89-96`, `docs/USER_GUIDE.md:438`).

The earlier recommendation to require an approved evidence set is withdrawn because it would contradict that product contract and reject legitimate hardware. No independent escape from STOP, fault combustion cut, or another hard output boundary was established in this finding. Retain graph/permutation tests for deterministic final-command previews and warning accuracy, but do not convert advisory sequence conventions into mandatory topology. If the UI does not already make the exact persistent commands at RUNNING entry obvious, improve that preview; that is a usability enhancement, not a pre-flash blocker.

### OT-AUD-046 — STOP cannot cancel Standby actuator/calibration outputs

The ordinary actuator tools deliberately run in STANDBY or the standby-like FAULT state and can energize the main fuel shutoff, both igniters, starter and starter-enable, main/secondary/AB pumps, AB solenoid, glow plug, air-starter valve, bleed valve, and arbitrary registry output (`src/main.cpp:2672-2741`, `src/main.cpp:2850-2935`). Firmware validators permit most test durations up to 60,000 ms (`src/system/Config.cpp:680-703`). Their only general termination mechanism is `checkToolTimers()`, which clears each demand after its deadline while the ECU remains in STANDBY/FAULT (`src/main.cpp:1203-1237`, `src/main.cpp:1255-1300`).

The supposedly emergency STOP command does not interact with that ownership. Its handler calls shutdown only in RUNNING or STARTUP, does nothing in SHUTDOWN, and has no STANDBY/FAULT branch (`src/main.cpp:2603-2609`). Thus web, cluster, or physical STOP during a main-fuel prime, igniter test, starter test, AB fuel test, or registry-output test leaves the output energized until the original timer expires. The Tools page also provides no cancel button for ordinary timed tools: after submission it locks all buttons and only updates a client-side progress bar; the dedicated Stop control exists only for Extra Cooldown (`data_src/tools.html:515-552`, `data_src/tools.html:571-610`). Closing the browser or losing Wi-Fi likewise cannot issue a cancellation, although the finite firmware timer prevents a permanent latch.

Calibration exposes a non-timed form of the same defect. `SET_OIL_PCT` writes both the live pump percentage and `_manualOilPct`, while `SET_OIL_DEMAND` writes a persistent pressure target; neither command creates an expiry deadline (`src/main.cpp:2655-2669`). The calibration page normally sends a zero from its explicit Stop/Cancel functions, but its unload/navigation handling has no corresponding fail-safe zero command (`data_src/calibration.html:1437-1474`; compare the telemetry-only unload handlers elsewhere in the page bundle). If the tab, browser, Wi-Fi link, or client fails after a nonzero command, the demand can therefore persist indefinitely in STANDBY, and pressing STOP still does not clear it. This directly contradicts the user-guide commissioning check that loss of browser/Wi-Fi must not leave a manual test running indefinitely (`docs/USER_GUIDE.md:491`).

Nor does holding the physical STOP input inhibit a new Standby test. Web command preflight checks standby-like mode, fitted hardware, and whether another output is already active, but it never checks `stopSwitchActive` for actuator/calibration commands (`src/system/web/WebServer.cpp:353-405`). Physical STOP polling updates the flag continuously yet acts only in STARTUP or RUNNING (`src/main.cpp:2980-3013`). Consequently, a continuously asserted STOP can coexist with a newly accepted fuel, ignition, starter, or other actuator test—the opposite of the intuitive emergency-interlock contract.

STOP should be an all-mode, synchronous safety action. Before any mode-specific transition, clear every tool deadline, manual demand, extra-cooldown/relight/AB action, and temporary registry demand, then call the physical hard-cut/all-off boundary appropriate to the current mode. An asserted STOP must also reject every subsequent energizing command until positively released. Manual calibration demands need a firmware lease/heartbeat timeout; a browser unload request is only a usability supplement. Add a prominent Cancel all outputs control on Tools and Calibration, but do not make browser availability part of the safety guarantee. Test STOP, held-STOP command attempts, and client disappearance from every millisecond-based tool and every manual/toggle tool in STANDBY and FAULT, at command-queue depths and ordering permutations covered by OT-AUD-041, and verify physical demand is zero on the same ECU-loop pass or bounded lease expiry.

### OT-AUD-047 — output-idle gate ignores device-backed I²C relays

`OutputActivity::anyPhysicalDemand()` is documented as the canonical logical-demand scan for every physical output, but it skips a channel whenever `c.pin < 0` before evaluating its demand (`src/system/OutputActivity.h:9-45`). That condition is valid only for direct GPIO outputs. An I²C relay is deliberately represented as an installed physical endpoint with `driver == I2cRelay`, device address/channel metadata, and `pin = -1`; hardware apply explicitly mirrors those channels into core actuator availability with a negative pin (`src/system/HardwareConfig.cpp:3775-3789`, `src/system/HardwareConfig.cpp:3805-3824`). Other availability checks correctly use `(pin >= 0 || driver == I2cRelay)` (`src/system/HardwareConfig.cpp:988-995`, `src/system/HardwareConfig.cpp:1237-1244`).

These omitted outputs are real and broad. `Hardware::updateRegistryOutputs()` maps main fuel shutoff, starter, starter enable, oil pump, both igniters, AB valve/pump, cooling/scavenge pumps, pilot fuel, glow plug, and other registry demands into I²C relay writes each actuator cycle (`src/Hardware.h:998-1024`). Nevertheless the activity scan reports false when such a channel is the only active demand. Its callers then allow OTA, factory reset, hardware/config operations that schedule reboot, and web START preflight to proceed on the premise that outputs are idle (`src/system/web/WebServer.cpp:214-215`, `src/system/web/WebServer.cpp:365-366`, `src/system/web/WebServer.cpp:408-409`, plus the update/reset/save gates that call `_outputsActiveForOta()`). Rebooting while a device-backed relay is energized is especially unsafe because an expander can retain its output latch until firmware later reinitializes it, and a missing device cannot be forced safe.

Define endpoint presence by driver: direct GPIO drivers require a valid GPIO, while `I2cRelay` requires a currently valid device/channel assignment. Then evaluate every installed physical endpoint's authoritative logical demand. Add table-driven tests for every output driver and core/non-core purpose at zero/nonzero/safe-demand states, and prove each gate—START, OTA, restore, hardware save, factory reset, and timed-tool mutual exclusion—rejects every physically active channel. This complements OT-AUD-028: even the web path that calls the canonical gate is currently incomplete.

### OT-AUD-048 — advertised I²C AB-flame sensor is not connected to AB runtime

The Hardware editor advertises `ab_flame` with direct digital/analog and I²C digital/analog drivers (`data_src/pages/hardware-registry-catalog.js:103-110`), and its adapter filter explicitly permits both digital and analog device-backed endpoints (`data_src/hardware.html:1267-1277`). The official S3 profile supplies TCA9554 digital inputs and TLA2528 analog inputs that can host those advertised modes (`pcb_profiles/official/openturbine-ecu-s3-v1.otpcb.json:21-25`, `pcb_profiles/official/openturbine-ecu-s3-v1.otpcb.json:51-112`, `pcb_profiles/official/openturbine-ecu-s3-v1.otpcb.json:206-214`). Generic registry sampling does read I²C input values and health into `registryInputValue/Healthy` (`src/Hardware.h:796-815`).

The AB-specific runtime never consumes them. Hardware topology resets `hasAbFlame` and then recognizes only installed `ab_flame` channels with `pin >= 0`, excluding both I²C drivers by construction (`src/system/HardwareConfig.cpp:4215-4227`). Sensor update similarly writes `ed.abFlameOn` and `ed.abFlameHealthy` only when `hasAbFlame && abFlamePin >= 0`; there is no registry lookup/mirror equivalent to the main combustor flame path immediately above it (`src/Hardware.h:1805-1839`, `src/Hardware.h:1860-1865`). By contrast, the UI's calibration and sequence surfaces infer availability directly from the registry purpose and will show the sensor as fitted (`data_src/calibration.html:708-713`, `data_src/sequence.html:2598-2607`).

In AB sensor-confirmation mode, `ABFlameConfirm` and running flame-loss monitoring consume the unwritten AB fields/`hasAbFlame`, so the supported configuration cannot confirm or monitor afterburner flame as represented to the user (`src/engine/sequencer/blocks/ABFlameConfirm.h:63-82`, `src/main.cpp:1881-1900`). The failure is generally fail-closed—ignition faults or validation treats the sensor as absent—so this is classified as P2 rather than an unsafe false confirmation, but it blocks the advertised tester configuration. Resolve one authoritative registry index for `ab_flame`, map both I²C digital and calibrated I²C analog values into AB health/value/sample telemetry, and use that same predicate for topology, validation, calibration visibility, confirmation, and running loss detection. Add adapter-matrix tests for drivers 0, 1, 8, and 9, including device loss and stale samples.

### OT-AUD-049 — ImmediateCut can be overwritten before any physical starter-off write

Normal/fault STOP first calls `cutCombustionAndStarterNow()`, which clears logical starter, starter-enable, and air-starter demands, then starts the configured shutdown sequence (`src/main.cpp:1139-1149`, `src/main.cpp:2015-2043`, `src/main.cpp:2046-2084`). It does not write the physical outputs synchronously. The default first block, `ImmediateCut`, is a one-tick action. `SequenceEngine::tick()` processes its Complete result and enters the next block in the same call, updating `EngineData.currentBlock` to (normally) `RPMDrop` before returning (`src/engine/sequencer/SequenceEngine.h:81-103`, `src/engine/sequencer/SequenceEngine.h:168-183`).

The rest of that ECU iteration then runs controllers and `RulesEngine::evaluate()` before `Hardware::updateActuators()` (`src/main.cpp:3398-3422`). A rule whose mode mask includes SHUTDOWN can therefore restore starter, starter-enable, or air-starter demand after both logical cuts. The final shutdown invariant always re-cuts combustion, but it re-cuts starter outputs only if `strcmp(ed.currentBlock, "ImmediateCut") == 0` (`src/Hardware.h:1115-1137`). That predicate is already false because the sequencer advanced. If the starter was running at STOP, the only physical write in this loop can consequently be another ON write; no OFF pulse ever reaches the driver before `RPMDrop`. An AB sequencer transition can independently overwrite the same shared block string (OT-AUD-044), making the predicate still less trustworthy.

The hard-cut requirement must be represented by an execution latch/generation, not display telemetry or an ephemeral block name. Set it before accepting STOP/fault, keep it asserted across all controller/rule evaluation, force combustion and every starter path off at the final actuator boundary, and clear it only after that physical update has completed (or retain it until an explicitly permitted later cooldown block takes ownership). Add an executable ordering test with each starter target commanded by an active SHUTDOWN rule, starter initially on/off, STOP from STARTUP/RUNNING, normal/fault paths, main plus AB sequencing, and direct/I²C outputs; assert at least one physical off write before any later cooldown re-enable.

### OT-AUD-050 — advertised I²C ADC threshold switches are rejected by firmware

The Hardware editor advertises driver `9` (`i2c_adc_digital_input`, labelled “Voltage-threshold switch”) for `start_switch`, `stop_switch`, `digital_switch`, `inhibit_start`, `estop`, `fault`, `low_oil_switch`, `oil_zero_switch`, `sequence_gate`, `ab_arm`, `ab_fire`, and `limp_mode` (`data_src/pages/hardware-registry-catalog.js:114-125`). Its compatibility logic also explicitly treats driver 9 as a valid switch adapter (`data_src/hardware.html:1267-1277`), so this is not merely a stale display label: the browser can construct and submit the configuration.

Firmware's registry contract disagrees. `ChannelRegistry::semanticDriverValid()` accepts only direct `Digital` or `I2cDigital` for every switch/interlock role and rejects `I2cAnalog` (`src/system/ChannelRegistry.h:416-433`). Driver 9 is serialized as `I2cAnalog`; `ChannelRegistry::add()` applies that semantic check, and full registry parsing consequently fails (`src/system/ChannelRegistry.h:260-288`, `src/system/ChannelRegistry.h:688-715`). `HardwareConfig::validateJson()` converts this to a generic `channel registry contents` rejection (`src/system/HardwareConfig.cpp:3153-3166`), and the Hardware PATCH endpoint returns only `400 {"error":"hardware patch rejected"}` (`src/system/web/WebServer.cpp:3002-3021`). Thus an adapter the editor specifically offers cannot be saved, across all twelve affected safety/control purposes, and the response does not identify the incompatible channel.

This is fail-closed and therefore P2, but it can consume scarce commissioning time and undermines confidence in the registry adapter contract immediately before tester distribution. Either implement the already-supported TLA2528 threshold/hysteresis sampling path for switch roles in firmware validation, or remove driver 9 from every affected UI definition. Generate the UI catalog from one authoritative firmware/schema source (or test both against a shared matrix), and add save/reload/runtime cases for every advertised purpose/driver pair plus precise per-channel validation errors.

### OT-AUD-051 — queued actuator commands have no execution acknowledgement

`POST /api/command` performs preflight on the asynchronous web task, pushes an `OTPacket`, and returns `200 {"ok":true}` as soon as the FreeRTOS queue accepts it (`src/system/web/WebServer.cpp:2062-2128`). The ECU loop later drains every queued packet in one pass (`src/main.cpp:3375-3381`, `src/system/CommandQueue.h:59-66`). Those are separate acceptance points: the HTTP response does not mean the Core-1 handler executed the action.

This distinction produces a reproducible ordering failure without a full queue. If two clients—or two requests issued before the next ECU drain—submit different timed actuator tests, both Core-0 preflights can observe no active demand and both queue successfully. During the later drain, the first handler sets its timer/demand. Every timed-test handler independently requires `!anyToolTimerActive()`; the second packet consequently does nothing and emits no result (`src/main.cpp:1223-1233`, `src/main.cpp:2673-2741`, `src/main.cpp:2850-2935`). State can also change between preflight and execution for other commands, producing the same accepted-then-ignored shape.

The Tools page treats HTTP 200 as execution: it immediately starts a local wall-clock progress bar labelled Active and disables controls (`data_src/tools.html:500-550`, `data_src/tools.html:585-616`). `/api/data` exposes extra-cooldown state but no authoritative command ID, accepted/rejected execution result, or ordinary timed-tool identity/deadline (`src/system/web/WebServer.cpp:1129-1143`), so polling cannot correct the false indication. This matters during commissioning because the operator may record “no click/no movement” as a wiring or actuator failure even though the ECU never ran that test.

Assign each command a monotonic request ID and publish a Core-1 result (`started`, `rejected` with reason, or `completed`) plus authoritative active-tool identity/deadline. For hazardous controls, the request handler should return `202 queued` and the browser should display Pending until that result arrives; never infer output activity from a client timer. Make timed-tool reservation atomic at the authoritative ECU boundary, and test simultaneous requests from multiple clients, queue ordering, mode changes, STOP, OTA/reboot transitions, and missing/disconnected telemetry.

### OT-AUD-052 — recovery lockout disappears after a second abnormal reset

The recovery mechanism retains only a complementary RTC pair indicating that the engine was active. `markActive()` sets it when START transitions to STARTUP; `markSafe()` clears it (`src/platform/esp32/PlatformInit.h:9-15`, `src/main.cpp:2569-2575`). At boot, an abnormal panic/watchdog/brownout arms `EngineData.recoveryLockout` only if that pair still says active. Immediately afterward, boot calls `ResetRecovery::markSafe()` unconditionally (`src/platform/esp32/PlatformInit.h:94-121`). The lockout itself is an ordinary RAM Boolean initialized false on every boot (`src/engine/EngineData.h:167-177`).

Therefore the required acknowledgement is not sticky. Reset A while STARTUP/RUNNING/SHUTDOWN is active produces the intended lockout. If Reset B occurs before the operator releases START, verifies the engine, and presses STOP, the new boot sees a cleared RTC marker and a freshly false RAM Boolean, so neither web nor ECU-core START gates block on abnormal-reset recovery (`src/system/web/WebServer.cpp:446-454`, `src/main.cpp:2361-2375`). Repeated brownouts or watchdog resets are precisely the environment where relying on a one-boot RAM flag is weakest. The UI message promises that STOP acknowledgement is required, but rebooting the controller state can remove that requirement.

The retained active predicate is also narrower than physical activity: standby/FAULT fuel prime, ignition, starter, throttle calibration, extra cooldown, persistent oil demand, and generic output tests never call `markActive()` (`src/main.cpp:2655-2935`). A reset during those actions therefore cannot arm recovery even on the first abnormal reboot. This compounds OT-AUD-042/046/047 for outputs or external expanders whose physical state cannot be proven safe across reset.

Represent `recovery_required` as the retained state, not merely the pre-reset mode. Set it before any engine or hazardous/manual output can energize; do not clear it during boot. Clear it only in the explicit STOP-acknowledgement path after START has been observed released and the final physical all-off boundary has completed. Use complementary value/inverse plus a version/check value, and decide deliberately whether NVS persistence is required across complete power loss. Fault-inject consecutive panic, task/interrupt watchdog, brownout, and power-cycle sequences at every mode/tool state; the invariant is that no START succeeds until the one explicit safe acknowledgement clears the marker.

### OT-AUD-053 — native safety DIs do not inhibit START during debounce

The ECU-core START gate checks the dedicated STOP input, timed/manual output ownership, and native DI channels whose role is exactly `inhibit_start`. It does not check native `estop`, `fault`, `low_oil_switch`, or `oil_zero_switch` channels (`src/main.cpp:2406-2477`). The web preflight is narrower still: `_startInhibitActive()` scans only native `inhibit_start` roles (`src/system/web/WebServer.cpp:412-425`). In contrast, the same ECU-core gate explicitly treats every registry `estop`/`fault` and enabled oil switch as a start-blocking safety role, including unavailable device-backed inputs (`src/main.cpp:2455-2473`).

An already debounced native safety input is normally caught later in the same loop before the physical actuator boundary, but that does not close the transition window. Native DIs update `ed.diState` only after the raw level has remained stable for `debounceMs`; firmware accepts 5–500 ms and defaults to 20 ms (`src/main.cpp:1467-1512`, `src/system/HardwareConfig.cpp:1686-1694`, `src/system/HardwareConfig.h:433-445`). Loop order is START/command handling, sensor and safety work, startup sequencer tick, then `checkGeneralDI()`, rules, and finally physical actuator writes (`src/main.cpp:3369-3422`). If an E-stop/fault asserts just before START while the debounced state is still false, START succeeds and the startup sequence can produce physical output writes on each loop until the debounce interval expires and the delayed level trip enters shutdown. At the maximum accepted setting this is a half-second start pulse while the safety contact is already physically active.

Safety permission and nuisance filtering must be separate. Before changing mode or calling the first startup block, sample every fitted native safety input's raw active level and block START immediately if any is active; also require the debounced healthy/inactive state if that is part of the installation contract. Keep debounce for declaring/reporting a running trip only if the hazard analysis supports that delay, and use a much tighter independent E-stop response. Consolidate dedicated STOP, legacy/native DI, registry direct GPIO, and registry I²C inputs behind one authoritative start-interlock predicate. Test assertion at every point in the debounce interval, all active-mode masks/polarities, held-at-boot state, disconnect behavior, and each web/physical/cluster START source.

### OT-AUD-054 — cosmetic theme changes perform active-mode flash writes

The storage design explicitly states that SPI-flash program/erase operations can suspend the other ESP32 core while caches are disabled, so LittleFS/NVS persistence must never run while the ECU is controlling an engine. `WebServer::tick()` consequently drains logs and deferred configuration/runtime-stat saves only in STANDBY or FAULT (`src/system/web/WebServer.cpp:3390-3410`). Core-1 callers use `Config::requestSave()` to set a RAM flag, and `Config::flushPendingSave()` performs the actual write later on Core 0 (`src/system/Config.cpp:1239-1254`).

The theme endpoint bypasses that invariant. `POST /api/theme?t=...` is deliberately not mode-gated; after copying the selected cosmetic key directly into `Config::uiTheme`, it calls `Config::save()` synchronously inside the async web callback (`src/system/web/WebServer.cpp:1853-1878`). `Config::save()` does not write a small preference record: it serializes both complete authoritative hardware and settings trees, writes `/ecu_config.tmp`, and renames the live file through `/ecu_config.bak` (`src/system/Config.cpp:1403-1461`). `theme.js` exposes this endpoint from every dashboard page (`data_src/theme.js:1-50`), so an ordinary appearance change during STARTUP, RUNNING, or SHUTDOWN can initiate the exact flash work the scheduler says is forbidden while outputs are active.

The storage mutex prevents two `Config::save()` calls from entering simultaneously, but it does not make an active-mode flash erase/program safe or join this write to `ConfigApplyGate`. Treat theme selection as RAM-only while active, set the existing deferred-save flag, and persist it only through the STANDBY/FAULT drain under the same transaction ownership as other settings. A host/state-machine test should issue theme changes throughout every mode, verify that no filesystem API is invoked until the all-safe boundary, and verify that simultaneous config/hardware writes cannot lose either the theme or engine settings. Consider keeping this purely per-browser in `localStorage`; if it remains part of the engine file, a cosmetic failure response should accurately distinguish RAM-applied from persisted state.

### OT-AUD-055 — Hardware Save misdetects selected-EGT safety enable events

The current public model has one **Turbine gas overtemperature** switch, `safety.overtemp`, which watches whichever TOT/TIT source is selected (`data_src/hardware.html:3610-3664`, `data_src/pages/config-schema.js:7-9`). Both limit fields explicitly support `0 = disabled`; this is part of the project's expert-setting contract, not an invalid value. Firmware accepts and preserves zero (`src/system/Config.cpp:553-562`, `src/system/Config.cpp:715-721`, `src/system/ConfigSerialize.cpp:669-672`, `src/system/ConfigSerialize.cpp:863`).

An obsolete split flag remains in runtime state. `HardwareConfig::safetyTitOvertemp` is initialized false, is not serialized, and `_fromDoc()` forces it false after treating legacy `safety.tit_overtemp` only as an alias that enables the unified `safetyOvertemp` flag (`src/system/HardwareConfig.cpp:2311-2322`, `src/system/HardwareConfigSerialize.cpp:285-295`, `src/system/HardwareConfig.cpp:4110-4119`). It therefore cannot represent the previous state of the current UI switch.

Nevertheless, the full Hardware POST snapshots that obsolete Boolean as `prevSafTit`, applies the submitted hardware document, sanitizes settings, and passes it to `Config::autoFillNewlyEnabledSafety()` (`src/system/web/WebServer.cpp:2785-2821`). The helper says it should fill only on an OFF→ON enable event so that deliberately setting a threshold to zero later remains respected. Instead it compares the always-false snapshot with `safetyOvertemp && hasTit`; whenever those are true and `titLimit <= 0`, it assigns 900 °C and persists the rewritten settings in the unified file (`src/system/Config.cpp:1102-1125`). Thus a user can deliberately save the documented zero TIT limit on Config, then make an unrelated Hardware edit, and have that setting silently changed to 900 °C. A TOT-only enable event is not represented by this branch at all, so the supposedly general enable-event policy is asymmetric.

Retire `safetyTitOvertemp` from active logic. Before applying a Hardware POST, snapshot the real unified `safetyOvertemp` state and the effective source/available limits. After apply, auto-fill the currently selected threshold only on a genuine false→true transition (or a source transition that newly makes a zero threshold authoritative), and return the auto-filled value explicitly in the save recap. Regression-test TOT-only, TIT-only, both-sensor automatic/explicit source selection, legacy `tit_overtemp` import, unrelated Hardware edits after a deliberate zero, and save/reboot round trips. This correction must preserve the user's ability to retain zero after knowingly accepting the Config warning.

### OT-AUD-056 — accepted Hardware layouts can exhaust LEDC resources

Every servo and variable-duty output consumes an ESP32 LEDC channel. This includes main throttle, starter, oil pump, primary/secondary igniters in PWM mode, afterburner pump, cooling/scavenge pumps, secondary/pilot fuel, bleed valve, prop pitch, glow/wet-glow output, and each registry `Pwm` or `Servo` channel (`src/Hardware.h:2090-2308`, `src/Hardware.h:955-989`). The passive buzzer also tries to allocate an LEDC channel on first use through the framework `tone()` implementation (`src/main.cpp:1159-1199`).

The pinned Arduino-ESP32 framework exposes only eight LEDC channels on ESP32-S3 (`SOC_LEDC_CHANNEL_NUM == 8`) and four timers in its single speed group. `ledcAttach()` chooses a free channel and requires either an existing timer with the exact frequency/resolution pair or an unused timer; it returns false when channels or compatible timers are exhausted (`framework-arduinoespressif32-libs/esp32s3/include/soc/esp32s3/include/soc/soc_caps.h`, `framework-arduinoespressif32/cores/esp32/esp32-hal-ledc.c:189-327` in the pinned PlatformIO package). Classic ESP32 has two speed groups and up to sixteen channel slots, so the budget is target-specific. Resolution fallback does not create capacity; it can create another distinct timer tuple.

OpenTurbine's hardware validation checks pins, electrical types, dependencies, endpoint collisions, and numeric PWM bounds, but never counts LEDC channels or distinct `(frequency,resolution)` timer tuples (`src/system/HardwareConfig.cpp:1356-1978`). The browser likewise permits all these outputs independently and has no target resource recap. A valid S3 document can therefore request more than eight proportional outputs, or fewer outputs using more than four incompatible timer configurations. It saves and schedules a reboot. Only during actuator initialization does `ledcAttach()` fail; core actuator readiness and registry PWM/servo initialization then set `hardwareReady = false`, which safely inhibits START but leaves the operator with a post-reboot initialization fault (`src/Hardware.h:955-989`, `src/Hardware.h:2309-2343`). Buzzer allocation can instead fail without joining that readiness check.

Build one target-aware LEDC allocator model used by firmware validation and the Hardware save recap. Count every core, auxiliary, registry, and buzzer consumer; normalize the resolution each driver will actually request; then ensure channels and timer-compatible groups can be assigned on the selected target. Reject impossible layouts before persistence with the exact outputs and frequency/resolution conflicts. Add boundary tests for S3 at 4/5 distinct timer tuples and 8/9 channels, Classic group allocation, shared 50 Hz servos, resolution fallback, registry/core mixtures, buzzer reservation, disable/re-enable, import, and PCB profiles. Runtime attach/readiness checks should remain as a second fail-closed layer.

### OT-AUD-057 — session-log retention is less durable than the Log page claims

The Session Data panel states, without qualification, that “Session files are kept until manually cleared” (`data_src/log.html:138`). Firmware implements a different and reasonable storage policy: before opening a session and whenever free space drops below 150 KiB, `_evictOldSessions()` repeatedly deletes the numerically oldest closed session until the reserve is restored (`src/system/SessionLogger.cpp:200-248`, `src/system/SessionLogger.cpp:261`). The deletion is reported only to Serial. There is no persisted `SESSION_EVICTED` event, telemetry counter, dashboard warning, or retention-capacity estimate, so a tester can follow the UI's explicit promise and still lose earlier CSV evidence automatically.

Keep automatic eviction—it protects the control filesystem—but make the contract truthful. Replace the absolute UI statement with a bounded-retention explanation, expose an eviction count/last-evicted run in telemetry or the event log, and warn when flash reserve is approaching the threshold. Test low-space startup, active download ownership, a current-session-only directory, deletion failure, and ordering across gaps/large run numbers. This is an evidence-retention and product-contract issue, not an objection to the eviction feature itself.

### OT-AUD-058 — thrust is omitted from the session CSV column-count diagnostic

`_csvColumnCount()` counts each enabled session mask and adds the four-column afterburner group and multi-column torque/loop groups, but it has no `SLOG_THRUST` branch (`src/system/SessionLogger.cpp:75-108`). The CSV header and row writer both correctly emit `thrust_n` when that mask is enabled (`src/system/SessionLogger.cpp:189-190`, `src/system/SessionLogger.cpp:296-297`). Consequently only the startup Serial line “N columns” is wrong, by exactly one, whenever thrust logging is selected (`src/system/SessionLogger.cpp:319-320`); CSV content is not lost or malformed. Add the missing count and generate the count/header/value parity test from one mask catalog so future channels cannot drift independently.

### OT-AUD-059 — per-boot session numbering breaks archive ordering after eviction

The durable lifetime count is `Config::runCount`; it is merged monotonically from the engine file and profile-keyed NVS and incremented on successful RUNNING entry (`src/system/Config.cpp:1269-1289`, `src/system/ConfigSerialize.cpp:615-626`, `src/main.cpp:1988-1991`). Session filenames do not use it. `_openSession()` starts its collision search at `EngineData::instance().runCount + 1`, a separate per-boot counter that returns to zero on every reboot (`src/system/SessionLogger.cpp:261-265`). This works only while files remain a contiguous `session_1.csv ... session_N.csv` chain: repeated existence checks happen to walk to the end.

Low-space eviction intentionally deletes the numerically smallest filenames first (`src/system/SessionLogger.cpp:200-248`). Once it removes the early part of that chain—for example, leaving sessions 95–100—a reboot starts searching at 1, sees it free, and writes the newest run as `session_1.csv`. The list endpoint also anchors on the per-boot counter and searches for an upward *contiguous* collision chain before walking downward (`src/system/web/WebServer.cpp:2232-2267`), so the surviving 95–100 files disappear from the dashboard after that reboot. On the next low-space pass, numeric ordering selects the brand-new session 1 as the oldest and deletes it before the genuinely old 95–100 evidence.

Use one monotonic durable session identity: start from `Config::runCount` and also recover the maximum valid filename at boot/open so storage remains authoritative after interrupted NVS writes or imports. Enumerate actual directory entries into the existing bounded 64-item response rather than relying on contiguity. Regression-test reboot before/after front eviction, gaps, a restored engine file, NVS lag, `UINT32_MAX`/filename limits, and verify that the newest physical run is never selected as the oldest merely because its filename wrapped or restarted.

### OT-AUD-060 — delayed maintenance reboot can interrupt newly active autonomous outputs

Firmware OTA, web-asset upload, Hardware Save, full engine-file restore, and factory reset all require STANDBY/FAULT and check `_outputsActiveForOta()` at admission (`src/system/web/WebServer.cpp:2178-2185`, `src/system/web/WebServer.cpp:2350-2366`, `src/system/web/WebServer.cpp:2460-2468`, `src/system/web/WebServer.cpp:2670-2681`, `src/system/web/WebServer.cpp:3060-3083`). After success, the latter operations schedule a delayed restart; OTA sets its own pending-restart flag. The ECU-core command handler rejects later energizing commands while maintenance/reboot is pending (`src/main.cpp:2318-2340`), which closes only the command path.

Autonomous output owners keep executing on every control tick. `checkStandbyOilFeed()` deliberately starts or regulates the oil pump when a selected shaft begins windmilling in STANDBY/FAULT (`src/main.cpp:1405-1459`), and `RulesEngine::evaluate()` runs afterward in every mode (`src/main.cpp:3410-3421`). Neither checks the maintenance or reboot flags. A nonzero intentional rule fallback can similarly become active after the initial idle snapshot. At the deadline, `_restartCleanly()` merely delays 250 ms and calls `ESP.restart()`; it neither re-evaluates `OutputActivity` nor calls `Hardware::allOff()` (`src/system/web/WebServer.cpp:1002-1013`, `src/system/web/WebServer.cpp:3450-3488`). Thus an upload can begin legitimately idle, an autonomous hardware-protection demand can start while bytes are written or during the five-second response window, and the ECU will reset unconditionally underneath it. A separately powered I²C expander can retain its last latch across that reset until initialization parks it again.

The one command explicitly exempted from both maintenance and reboot rejection is also not guaranteed to be de-energizing. The web preflight says `AB_STOP` “only de-energizes outputs” and allows it while every other command is blocked (`src/system/web/WebServer.cpp:353-360`, `src/system/web/WebServer.cpp:2113-2124`). `enterABShutdown()` hard-cuts AB fuel first but then starts the user-configurable AB-shutdown sequence with unrestricted enter/exit side actions (`src/main.cpp:1694-1715`). Those actions can target main fuel, starter, pumps, valves, or registry outputs, so an allowed AB_STOP can create a new non-AB demand during the very upload/reboot interval that assumes commands cannot energize anything. OT-AUD-063 covers the result-insensitive exit behavior; this is a separate confirmation that the maintenance quiescence premise is incomplete even without an autonomous rule or windmilling-oil transition.

Do not solve this by disabling windmilling oil protection silently. Before flash writes begin, enter an explicit maintenance state that resolves all allowed autonomous owners and proves the intended output policy; if protective oil must remain available, abort/defer maintenance when it activates. Recheck authoritative physical demand immediately before restart and postpone or cancel the reboot when it is nonzero. If a deliberate all-off restart policy is chosen, perform and verify `Hardware::allOff()` before clearing the retained active/recovery marker and before `ESP.restart()`. Test each maintenance operation with shaft speed crossing the standby-oil threshold, pressure-loop fallback, rules turning on/off, I²C relay heartbeat/loss, FAULT mode, and demand changes immediately before the deadline.

### OT-AUD-061 — log deletion does not discard already queued events

The Log page says Clear Event Log “will permanently delete all recorded events,” and factory reset promises to erase event and session logs (`data_src/log.html:527-535`, `data_src/tools.html:1068-1085`, `docs/USER_GUIDE.md:517`). Event producers do not write directly to LittleFS; they enqueue records in a bounded RAM ring for later STANDBY/FAULT draining (`src/system/FlightRecorder.cpp:27-54`, `src/system/FlightRecorder.cpp:561-589`).

`CLEAR_LOG` only sets `s_clearPending` (`src/main.cpp:2791-2797`, `src/system/FlightRecorder.cpp:316-318`). In `runEviction()`, the clear branch removes the file and resets its line count, but it does not advance `s_ringTail`, reset the dropped-event marker, or establish a generation boundary; `_drainRingLocked()` runs immediately afterward in the same call and writes every pre-clear queued record back into a newly created log (`src/system/FlightRecorder.cpp:530-556`). Factory reset is weaker: its HTTP handler removes `FlightRecorder::PATH` directly without even setting the clear flag (`src/system/web/WebServer.cpp:2192-2230`), while the five-second pending-reboot window continues calling `FlightRecorder::runEviction()` in STANDBY/FAULT (`src/system/web/WebServer.cpp:3394-3403`). Any queued pre-reset records can therefore survive the promised wipe on flash.

Treat clear/reset as an atomic event-generation barrier under `s_ringMux`: delete or generation-invalidate every record queued before the accepted clear, reset associated dropped markers as defined by the product contract, then remove the file while the consumer is excluded. Records genuinely generated after the barrier may be retained, but must be distinguishable as post-clear. Factory reset should suppress further log persistence until reboot and verify no event/session file remains. Add races for producer-before/during/after clear, full-ring overwrite, active raw download, file-delete failure, factory-reset delay, and reboot recovery.

### OT-AUD-062 — GovernorHold cannot verify governor control in its actual mode

The Sequence editor labels `GovernorHold` as **Wait for N2 Speed Control** and says to use it “after entering RUNNING to confirm the governor has taken control”; it further claims that on timeout “the engine is already in RUNNING” and the governor will continue regulating (`data_src/pages/sequence-definitions.js:623-633`). No startup block enters RUNNING. The main sequencer remains in `SysMode::STARTUP` until its final block completes and the sequence callback calls `enterRunning()` (`src/main.cpp:2245-2252`).

The controller lifecycle makes the mismatch executable, not cosmetic. `Hardware::initControllers()` calls `g_ctrlGovernor.begin()` only inside `enterRunning()` after the whole startup sequence has completed (`src/main.cpp:1982-2012`, `src/Hardware.h:2600-2615`). `Hardware::runControllers()` is called during STARTUP, but explicitly ticks the governor only when `mode == RUNNING` (`src/Hardware.h:2678-2750`). `GovernorHold::tick()` therefore watches raw N2 approach the target without governor authority and returns Complete either when it happens to enter the band or when its timeout expires—even with unhealthy feedback (`src/engine/sequencer/blocks/AdvancedBlocks.h:198-224`). Only afterward does RUNNING begin and the unproven governor take control.

Preserve the user's freedom to omit the block or accept a bounded monitoring timeout, but do not claim it verifies control that is not active. Either introduce an explicit late-startup governor ownership phase with well-defined fuel/pitch arbitration and safety limits, or redefine the block as passive “wait for N2 band” monitoring and add a separate RUNNING governor-engagement/settling mechanism. Tests must prove controller initialization/ticks occur during any claimed verification interval, N2 health loss has the documented result, timeout semantics are truthful, and throttle/pitch ownership transfers without a discontinuity.

### OT-AUD-063 — a failed sequence block still executes its ordinary exit side actions

`SequenceEngine::tick()` calls the configured per-block exit-action list not only for `Complete`, but also before dispatching every real `Abort` and `Fault` callback (`src/engine/sequencer/SequenceEngine.h:93-96`, `src/engine/sequencer/SequenceEngine.h:106-124`, `src/engine/sequencer/SequenceEngine.h:127-144`). Forced replacement and `stopSequence()` do the same (`src/engine/sequencer/SequenceEngine.h:40-49`, `src/engine/sequencer/SequenceEngine.h:62-69`). These are not cleanup-only actions: `_applyActions()` passes each configured value to the unrestricted global actuator-demand mapping, which includes throttle, starter/enable, main fuel solenoid, both igniters, pumps, valves, prop pitch, and registry outputs (`src/engine/sequencer/SequenceEngine.h:185-191`, `src/system/RulesEngine.h:340-386`). The browser exposes that same global actuator catalog for each startup, shutdown, AB-ignition, and AB-shutdown action list (`data_src/pages/sequence-state.js:103-115`).

The afterburner fault path proves an actual unsafe survivor rather than a merely transient internal assignment. If `ABFlameConfirm`, `ABStabilize`, or a custom AB block returns Fault, its exit side action runs first. `abSequenceFault()` then clears AB solenoid, AB pump, AB fuel offset, and igniter 2, but it does not clear main throttle, starter, starter enable, main fuel solenoid, main igniter, or arbitrary registry outputs (`src/main.cpp:1780-1790`). The control loop calls `g_abSequencer.tick()` and later `Hardware::updateActuators()` in the same iteration (`src/main.cpp:3400-3421`), so an AB block configured with an exit action such as main fuel ON or starter ON physically commands that output precisely because AB ignition failed. The equivalent Abort cleanup has the same target gap (`src/main.cpp:1758-1778`). This is independent of OT-AUD-040: it uses the editor-supported side-action mechanism and does not require importing a wrong-context block.

Do not remove expert side actions. Give them explicit result semantics. Ordinary **on successful exit** actions should run only after `Complete`; Abort, Fault, forced stop, and sequence replacement should run ECU-owned fail-safe cleanup or separately configured failure actions constrained by sequence context and hard output invariants. At minimum, an AB terminal failure must not be able to leave any newly asserted unrelated demand for the actuator writer. Regression-test every result (`Complete`, `Abort`, `Fault`, bench-skip, replacement, forced stop), each sequence context, all hazardous targets, callback re-entry/generation changes, and verify the physical demand snapshot immediately before the actuator write.

### OT-AUD-064 — cooldown eligibility misses physically commanded fuel paths

`fuelEverOpened` decides whether a startup Abort goes through the full shutdown sequence or directly to STANDBY (`src/main.cpp:2224-2239`), and `CooldownSpin` skips all cooling as soon as that flag is false (`src/engine/sequencer/blocks/CooldownSpin.h:24-36`). That makes it a safety-history latch: once any path can have admitted combustible fuel, it must remain true until the attempt reaches its safe terminal boundary.

The latch is not derived from all physical fuel commands. The main throttle actuator sets it at the final write when effective demand is nonzero (`src/Hardware.h:2360-2374`), and several stock fuel-pump blocks set it explicitly. `FuelPulse`, however, physically opens the main fuel solenoid and explicitly declines to set the latch because it is *intended* for pre-ignition priming (`src/engine/sequencer/blocks/MoreBlocks.h:8-42`). The editor permits arbitrary sequence ordering, while firmware validation merely warns that FuelPulse is not sustained delivery; it does not constrain the pulse to precede ignition (`src/main.cpp:703-739`). A user can therefore place the supported pulse after an ignition action, abort later, and receive neither the shutdown sequence nor hot cooldown even though a combustible pulse may have lit.

The gap is wider for the advertised expert mechanisms. Sequence side actions and custom action steps call `RulesEngine::applyActuatorDemand()` (`src/engine/sequencer/SequenceEngine.h:185-191`, `src/main.cpp:193`), whose fuel-solenoid and secondary-fuel-pump targets only assign their demand fields (`src/system/RulesEngine.h:340-386`). The final writers operate those outputs without setting `fuelEverOpened` (`src/Hardware.h:2400-2540`). Registry fuel/pilot outputs likewise write their demand with no fuel-history update (`src/Hardware.h:993-1025`). Thus a sequence can physically command fuel by supported generic mechanisms, then have a later Abort take the no-fuel direct-STANDBY path; a normal STOP can run the shutdown sequence but `CooldownSpin` still skips as no-fuel.

Keep arbitrary ordering and fuel-control mechanisms. Move the invariant to the authoritative output boundary: any nonzero effective main-fuel, shutoff/admission, secondary/pilot/wet-glow fuel, or other purpose classified as fuel must atomically latch actual fuel use before its physical write. Conservative false positives cost a cooldown; false negatives can omit oil/spindown/cooling after combustion. Define separately whether AB-only fuel during an already-running main engine changes this latch. Test every stock block, custom action, enter/exit side action, control rule, registry driver/purpose, wet-glow path, minimum-demand lift, aborted pulse, and STOP/Fault timing before/during/after the first physical nonzero write.

### OT-AUD-065 — destructive erase endpoints report success without proving erasure

`DELETE /api/session/all` returns `{"ok":true}` even when `/logs` cannot be opened and ignores the Boolean result of every `LittleFS.remove()` call (`src/system/web/WebServer.cpp:2130-2161`). The client therefore cannot distinguish a completed wipe from storage failure or a partially deleted directory. The Log page presents this as **Delete All Sessions**, so a tester may reasonably rely on the success response before distributing or resetting an ECU.

Factory reset has the same issue across more authoritative state. It schedules an unconditional reboot before attempting erasure, then ignores removal results for the unified engine file, legacy hardware file, event log, and every session file (`src/system/web/WebServer.cpp:2168-2228`). `Config::clearRuntimeStats()` returns `void`; failure to open NVS is only printed to Serial, and the individual `Preferences::remove()` results are ignored while RAM counters are zeroed anyway (`src/system/Config.cpp:1362-1382`). The handler always sends HTTP 200 `{"ok":true}`. If `/ecu_config.json` removal fails, the scheduled reboot can simply reload the old engine/hardware configuration after the UI has stated that factory reset succeeded. If only some deletes fail, the result is an undocumented partial reset.

The Event Log clear path has the same unchecked filesystem postcondition even apart from the queued-event resurrection in OT-AUD-061. Both `FlightRecorder::clear()` and the deferred clear branch in `runEviction()` ignore `LittleFS.remove(PATH)` and reset the in-memory line count/clear request regardless (`src/system/FlightRecorder.cpp:309-318`, `src/system/FlightRecorder.cpp:530-552`). Its low-space last-resort eviction also treats a failed removal as a successful fresh log (`src/system/FlightRecorder.cpp:438-459`). OT-AUD-051 separately covers the command queue's premature HTTP acknowledgement; this finding covers the storage layer having no success/failure result that the command path could eventually report.

Treat each destructive operation as a verified transaction. Do not send success until required files are absent and runtime-stat keys are confirmed absent; explicitly define which optional/legacy cleanup failures are warnings versus reset failures. A reboot already scheduled before the write cannot be cancelled, so either perform and verify the wipe before arming restart or persist a boot-time reset transaction that retries to completion and reports its result after reconnect. Directory deletion should enumerate a stable snapshot (or repeatedly enumerate until no matching entries remain), check every close/remove result, and return the exact undeleted items. Inject open/remove/NVS failures, partial directory iteration, power loss at every step, and confirm that no response or post-reboot page claims erasure unless the defined postcondition holds.

### OT-AUD-066 — session-log storage failures are invisible in the UI

`SessionLogger` maintains an explicit health/error channel. Queue-allocation failure sets error 1, session-file open failure sets error 2, header failure sets error 3, backlog loss sets error 4, low space sets error 5, and row-write failure sets error 6 (`src/system/SessionLogger.h:25-26`, `src/system/SessionLogger.cpp:197-203`, `src/system/SessionLogger.cpp:251-318`, `src/system/SessionLogger.cpp:418-428`). `/api/data` publishes both `session_logger_healthy` and `session_logger_error` (`src/system/web/WebServer.cpp:1159-1162`).

The browser never consumes either field. The only dashboard indication is driven by `session_dropped_rows > 0` (`data_src/app.js:764-770`, `data_src/index.html:68-70`). Queue allocation and file-open failures set unhealthy/error but do not increment that counter, so they produce no banner. A failed open also clears `currentPath`; the Log page consequently gives only the ordinary absence text, “No current session log,” or a generic download failure (`data_src/log.html:633-647`, `data_src/log.html:847-854`). Nothing tells a tester that the requested run was not persisted because logging failed.

Show a persistent, decoded logger fault on the dashboard and Log page, keep it visible across reconnect until a later session proves recovery or the user acknowledges it, and distinguish “no run yet” from “run capture/persistence failed.” Include the affected run/path when known. Browser tests should inject every documented logger error code, including zero dropped rows for queue/open failures, and verify accessible visible text rather than merely API fields.

### OT-AUD-067 — one calibration save treats rejected HTTP responses as success

The fuel-pump-minimum calibration uses a one-off PATCH response chain instead of the page's checked `patchConfig()` helper. It parses JSON and throws only when `body.ok === false`; it never tests `Response.ok` (`data_src/calibration.html:1553-1563`). On the apparent-success branch it updates the displayed saved value, states “Saved … as the fuel-pump minimum spin,” and stops the test output.

Several normal server rejections deliberately return an error object without an `ok` member: maintenance upload in progress returns HTTP 423, the active-mode configuration lock returns 423, and an apply-gate race returns 409 (`src/system/web/WebServer.cpp:1734-1759`, `src/system/web/WebServer.cpp:1787-1817`). For each, `body.ok` is `undefined`, the condition is false, and the UI reports success despite no persistence. This can happen if another tab begins maintenance/configuration or the engine state changes between the calibration page's standby check and the request. Validation/storage failures happen to include `ok:false` and are caught, which makes the bug response-shape-dependent.

Use the same `!r.ok || body.ok === false` rule as `postCalCommand()`, `patchHardware()`, and `patchConfig()`, and update the displayed saved value only after that check. Add a browser contract test that injects every non-2xx response shape for every mutating fetch and asserts no success text/local-state commit occurs.

### OT-AUD-068 — persistent runtime-stat write failure loses its retry and remains invisible

Start attempts, successful RUNNING entries, and accumulated run seconds are updated on Core 1 and set one deferred NVS-write flag (`src/main.cpp:1989-1990`, `src/main.cpp:2116-2119`, `src/main.cpp:2584-2585`). When STANDBY/FAULT permits storage work, `flushPendingRuntimeStats()` clears that flag before opening or writing NVS. If `Preferences::begin()` fails or any `putUInt()` returns zero, it prints a warning and returns false without restoring the dirty flag (`src/system/Config.cpp:1255-1260`, `src/system/Config.cpp:1290-1320`). `WebServer::tick()` ignores the return value (`src/system/web/WebServer.cpp:3403-3411`). Unless a later run happens to set the flag again before power loss, the latest counters are lost on reboot.

Meanwhile `/api/data` identifies `run_count` as a “persisted lifetime count,” publishes the start count and cumulative seconds, and the dashboard labels them “Cumulative engine run statistics stored in persistent flash memory” (`src/system/web/WebServer.cpp:1340-1352`, `data_src/index.html:470-476`, `data_src/app.js:886-894`). The values remain correct in RAM after a failed write, so no visible discrepancy exists until reboot silently rolls them back. This also aggravates OT-AUD-059 because the start-attempt counter is used as a session-file identity source.

Keep the dirty bit set until all keys are durably written, retry with bounded backoff at safe storage boundaries, and expose `runtime_stats_persisted`/last error separately from the live totals. A coherent multi-key record with a version/checksum is preferable to three independently updated keys. Inject begin and each-key write failure, reboot immediately after failure, and counter increments racing the flush.

### OT-AUD-069 — event-recorder persistence failures have no health signal

The event recorder correctly keeps an event at the ring tail when opening `/logs/events.jsonl` or appending a line fails, so a transient filesystem error can be retried (`src/system/FlightRecorder.cpp:470-528`). But it records no error state, retry count, or unpersisted-event count. The only telemetry/UI warning is `event_dropped_events`, which increments only after the small RAM ring becomes full and overwrites/rejects records (`src/system/FlightRecorder.cpp:27-54`, `src/system/FlightRecorder.cpp:561-589`, `src/system/web/WebServer.cpp:1163-1164`, `data_src/app.js:772-778`). A persistent open/write failure after one or several important events can therefore leave those events solely in volatile RAM with a zero dropped count; power loss then removes the evidence with no prior visible warning.

Initialization has adjacent blind spots. `FlightRecorder::begin()` ignores `/logs` creation and backup-recovery results and cannot report mutex-allocation failure (`src/system/FlightRecorder.cpp:66-77`). More broadly, failure to allocate the Core-0 `webTask` is printed to Serial but does not set an ECU health field (`src/main.cpp:3104-3114`, `src/main.cpp:3249-3252`); that task is the only caller that drains both event and session queues at safe storage boundaries. REST controls may still be reachable through the async server while neither log is being persisted.

Expose recorder queue depth/unpersisted count, last filesystem error, mutex readiness, and maintenance-task readiness. A successful drain should clear a transient warning only after the file can be reopened/read and the expected tail is present. For a tester campaign that relies on logs, make logging-health failure a visible test-inhibit condition even if it is not a general engine START interlock. Inject mkdir/mutex/task/open/append/eviction failure and reboot with fewer pending events than the ring-overflow threshold.

## Focused afterburner system review

This pass traced the stock and custom AB light-up/shutdown sequences, all four trigger modes, arm gating, flame/EGT/timed confirmation, torch and dedicated ignition, pump scheduling, main-fuel coordination, output binding, dashboard/config/hardware/sequence/log surfaces, cluster fields, documentation, and both AB HIL campaigns. It also compared the operator model with official descriptions of automatic afterburner control and timed pilot-flame/spark/hot-shot ignition. The review preserves sensor-light and unconventional hobby installations. Timed assumption, unusual sequencing, manual control, and user-accepted warnings remain legitimate features; the new P1 findings are cases where the implementation can defeat a hard protection or declare/maintain combustion without the evidence its selected mode claims to use.

### OT-AUD-070 — AB main-fuel coordination bypasses gradual throttle protection

`ThrottleSlew::tick()` is the authoritative gradual protection stage. It applies missing-feedback freeze, N1/N2/EGT/P1/P2/torque pullback, predictive approach softening, and opening/closing rate limits, then writes the protected `_current` back to `ed.throttleDemand` (`src/engine/controllers/ThrottleSlew.h:81-188`). The normal loop deliberately runs controller/rule demand creation before `Hardware::applyThrottleProtection()` and the physical actuator write (`src/Hardware.h:2680-2765`, `src/main.cpp:3403-3421`).

AB coordination is composed later. While Running, `checkABTrigger()` stores `abMainFuelOffsetPct` independently in `ed.abFuelOffset` (`src/main.cpp:1901-1909`). `Hardware::updateActuators()` then adds that offset to the already protected throttle just before `g_actThrottle->set()` (`src/Hardware.h:2358-2374`). The only protection repeated after composition is the reduced-power cap. A positive AB offset can therefore undo a gradual overspeed, overtemperature, pressure, or torque pullback and can step around the configured throttle opening ramp. Hard trips may react on a later sensor sample, but the soft layer exists to avoid reaching them.

Keep the useful coordination feature, including negative offsets. Compose it into the demand before the authoritative slew/pullback stage, or calculate an effective final cap/rate-limited demand that no later additive owner can exceed. Display and log requested main demand, AB offset, protected ceiling, and actual output separately. Add executable vectors for every pullback source at 0/positive/negative offsets, predicted-limit approach, governor ownership, throttle ramp, reduced power, and simultaneous AB light-up.

### OT-AUD-071 — EGT-rise evidence starts measuring after the light-up event

The stock order is `ABSolOpen -> ABPumpOn -> ABIgnite -> ABFlameConfirm` (`src/main.cpp:1678-1686`). `ABIgnite` turns on the AB igniter and/or applies the torch offset for the complete configured torch duration before returning Complete (`src/engine/sequencer/blocks/ABIgnite.h:35-109`). Only when the sequencer enters the following block does `ABFlameConfirm::onEnter()` capture `_totBaseline` (`src/engine/sequencer/blocks/ABFlameConfirm.h:29-40`). Any selected-EGT rise caused during the actual ignition action is therefore discarded; the confirmation block demands another full rise after ignition has already occurred. A successful light can be rejected, encouraging a builder to increase fuel/time or fall back to unverified timed mode.

At the other boundary, firmware accepts `totRiseDegC == 0` and the Config input explicitly permits zero (`src/system/ConfigSerialize.cpp:889-906`, `data_src/config.html:292-297`). Because confirmation is `rise >= totRiseDegC`, the first healthy sample confirms a nominal “EGT-rise verification” without any rise (`src/engine/sequencer/blocks/ABFlameConfirm.h:84-103`).

Create an AB-attempt context before the first fuel/ignition action and snapshot a fresh selected temperature there. Confirmation should consume that immutable baseline plus sample timestamps, require a strictly positive installation-appropriate threshold, and reject stale/noisy evidence. If a custom sequence intentionally needs a later baseline, expose it as an explicit baseline-capture step rather than silently changing the meaning of “rise.” This complements OT-AUD-039: correct block order alone does not repair the stock baseline boundary.

### OT-AUD-072 — flame-sensor confirmation can accept a stuck-high or transient signal

`ABCheckReady` validates N1, selected EGT, throttle, and main mode, but never checks that a fitted AB flame detector is healthy and OFF before fuel admission (`src/engine/sequencer/blocks/ABCheckReady.h:29-86`). Sensor-mode `ABFlameConfirm` later completes as soon as `ed.abFlameOn` is true (`src/engine/sequencer/blocks/ABFlameConfirm.h:61-74`). It requires neither a pre-attempt OFF sample nor an OFF-to-ON transition, and unlike running flame loss it has no dwell. A failed-high detector or one noisy high sample can therefore declare light-up and leave AB fuel active.

The direct analog threshold sensor also reports every fitted rail state as healthy, so a generic disconnected/shorted detector cannot be distinguished from a valid steady state (`src/Hardware.h:1860-1865`). OT-AUD-048 separately covers advertised I2C sensors not reaching these fields; connecting those adapters without fixing acquisition semantics would reproduce the same false-positive path.

Before fuel, require a configurable healthy flame-OFF dwell and record the detector's raw/value range. After fuel/ignition, require a fresh stable OFF-to-ON transition with acquisition dwell and threshold hysteresis. Allow an explicit bypass only when the operator selects timed/unverified mode; do not label a level that was already high as verified light-up. Test stuck low/high, noisy crossings, stale/reconnected sensors, active-low adapters, and signal assertion before, during, and after each causal action.

### OT-AUD-073 — stabilization can lose flame and still declare AB Running

`ABStabilize` monitors only an optional selected-EGT ceiling and elapsed time. When the hold completes it unconditionally sets `abMode = Running` (`src/engine/sequencer/blocks/ABStabilize.h:25-54`). The global flame-loss monitor does not run while mode is Igniting; it is entered only by the `ABMode::Running` case and only when the configured confirmation mode is the dedicated sensor (`src/main.cpp:1881-1900`). Thus a sensor-confirmed flame can disappear immediately after `ABFlameConfirm` exits, remain absent through the full stabilization hold, and still be declared Running. The monitor notices on the next Running tick, then intentionally waits the configured loss delay before cutting fuel.

EGT-rise and timed modes have no running combustion supervision at all, even when a separate detector becomes available. This is not an argument to remove sensorless operation; it means “how light-up is confirmed” and “how an established burn is supervised” are currently coupled into one choice when hobby hardware may provide different useful signals.

Keep the selected acquisition evidence valid throughout stabilization, including continuous sensor assertion or a configurable post-rise EGT condition. Separate optional running supervision from light-up confirmation, with sources such as dedicated flame, AB exhaust temperature, pressure, or explicitly none, and configurable actions/dwell. Transition to Running in the state machine only after the complete evidence policy passes; a freely placed block should not own that transition (also OT-AUD-039).

### OT-AUD-074 — custom AB light-up has no independent fuel-on deadline

The editor deliberately permits `TimedDelay` in AB ignition, and imported per-slot delays are accepted up to 3,600,000 ms (`data_src/pages/sequence-definitions.js:137-145`, `src/system/HardwareConfig.cpp:4235-4258`). `TimedDelay` preserves every prior output while it waits (`src/engine/sequencer/blocks/TimedDelay.h:8-25`). Firmware requires only that a custom AB list contain `ABFlameConfirm`; it does not bound when that block is reached (`src/main.cpp:940-959`, OT-AUD-039). Consequently `ABSolOpen -> ABPumpOn -> TimedDelay -> ABFlameConfirm` can admit AB fuel for the entire delay before the confirmation block's own timeout even begins.

This is a hard-envelope issue, not a request to remove custom ordering. Start a supervisory hazardous-light-up timer at the first effective AB fuel admission and require confirmed, stabilized burn or fuel-off before its configurable maximum. The deadline must be independent of block order, delays, custom blocks, side actions, mode labels, and whether the valve or pump is the actual admission device. Exceeding it must synchronously cut AB fuel before normal exit actions and store a precise reason. Generate permutations with each fuel owner and delays at UI/import boundaries.

### OT-AUD-075 — AB trigger and arm signals have no conditioning policy

Throttle mode compares one protected demand to one threshold; switch and arm modes read raw `digitalRead()`/registry levels; analog and RC compare one normalized sample to one threshold (`src/main.cpp:1819-1850`, `src/Hardware.h:1866-1881`). The same threshold turns an automatic AB both on and off, with no hysteresis. Direct AB switch/arm paths have no debounce, analog/RC paths have no assertion or release dwell, and the state machine has no minimum on/off time. A release during Igniting immediately begins shutdown, while a later fresh edge can begin another light-up (`src/main.cpp:1871-1946`). Mechanical bounce, RC jitter, ADC noise, or hovering throttle can therefore cause nuisance aborts or repeated light/stop attempts.

The rendered Hardware workflow exposes signal type, polarity, one threshold, and optional arm; the Sequence page describes shutdown at that same threshold. Neither surface offers or discloses conditioning. Registry analog threshold inputs have an electrical hysteresis field, but the dedicated AB trigger contract does not expose one coherent source-independent policy.

Add separate assert/release thresholds, configurable dwell/debounce, and minimum on/off/rearm times, with source-appropriate conservative defaults. Preserve a deliberate zero-delay expert option where the signal is already externally conditioned, but show the resulting warning. Log raw, normalized, conditioned, arm-gated, and edge-latched states so a builder can tune the setting without fuel.

### OT-AUD-076 — AB faults and tuning evidence are not diagnosable from the product UI

AB Abort/Fault callbacks clear core AB demands and set only the coarse `ABMode::Fault`; they do not retain a code, failed block, gate value, baseline, peak rise, timeout, or retry requirement (`src/main.cpp:1758-1790`). The AB blocks print useful detail only to Serial and do not publish a persistent wait/failure reason. `/api/data` exports mode, raw trigger, arm, flame level, valve, and pump, but omits AB flame health, AB input raw/normalized/valid, the AB igniter in the AB card, conditioned trigger/gate state, and an AB-specific fault reason (`src/system/web/WebServer.cpp:1171-1191`). The dashboard consequently shows only `FAULT`; its generic `fault_description` belongs to the main engine.

Session logging records only `ab_mode,ab_flame,ab_pump_pct,ab_offset_pct` (`src/system/SessionLogger.cpp:145-154`, `src/system/SessionLogger.cpp:297`). The event recorder stores only AB mode and pump percentage in snapshots (`src/system/FlightRecorder.cpp:120-132`). It omits the trigger/arm/input, solenoid, igniter, detector health/raw value, selected evidence, attempt baseline/rise, and terminal reason most useful to a DIY builder. The current AB HIL campaign explicitly enables Bench Mode, which bypasses sensor/EGT confirmation, and checks only happy-path fire/stop plus running sensor-loss dwell (`dev/bench/campaign/afterburner_test.py:1-82`); the limp campaign also uses Bench Mode (`dev/bench/campaign/afterburner_limp_hil.py:35-41`).

Give each attempt an ID and retained terminal record: source, raw/conditioned trigger, arm gate, readiness values, first fuel time, ignition actions, evidence source/baseline/current/peak, failed block/result, fuel-cut time, and retry rule. Show concise current guidance on the dashboard and full detail in Log. Separate main and AB sequencer progress first (OT-AUD-044). Add host-native state-machine tests for every evidence/fault path; physical HIL can later validate the sensor and actuator waveforms.

### OT-AUD-077 — legacy `ab_fire` DI semantics disagree with Physical-switch mode

On a rising native/legacy DI edge with role `ab_fire`, `checkGeneralDI()` directly calls `handleCommand(AB_FIRE)` and describes it as equivalent to the dashboard button (`src/main.cpp:1543-1568`). The command is accepted only when `abTriggerSource == 0` (Manual) (`src/main.cpp:2799-2810`). Source 2 (Physical switch), meanwhile, level-polls only a registry input with purpose `ab_fire` or the dedicated `abSwitchPin`; it never consumes `ed.diState[]` for a legacy `ab_fire` (`src/main.cpp:1819-1840`). A restored/migrated legacy DI labelled AB fire can therefore be valid and visibly change state yet do nothing when the operator selects the matching Physical-switch source.

Registry `ab_fire` happens to work under source 2 because the state machine polls its level, even though the general DI path also emits a rejected manual command on its rising edge (`src/main.cpp:1605-1616`). Normalize both representations into one canonical raw/healthy/conditioned AB request and let the configured source decide level versus edge behavior once. Firmware validation should either migrate a legacy channel automatically or reject the incompatible combination with the exact repair. Test native, registry GPIO, I2C digital, and dedicated-pin variants across all sources and active-mode/polarity settings.

### OT-AUD-078 — throttle mode conflates pilot request with permission and protected output

The trigger advertised as **Throttle threshold** is not evaluated from the pilot's calibrated stick/axis request. When a main fuel output is fitted, `checkABTrigger()` compares `g_ctrlThrottleSlew.currentDemand()`—the protected, rate-limited physical fuel demand—to `abThrottleThreshold` (`src/main.cpp:1819-1830`). That value is also changed by governor action, dynamic idle, missing-feedback freeze, and all soft pullbacks. The product therefore has no separate Boolean for “the pilot is beyond the AB detent” versus “the engine is currently permitted to light or sustain AB.”

On the rising edge, firmware immediately starts the light-up sequence. `ABCheckReady` is a one-tick check and returns Abort—not Waiting—when N1 is below its configured minimum, above its maximum, or selected EGT is too hot (`src/engine/sequencer/blocks/ABCheckReady.h:29-86`). Abort becomes `ABMode::Fault`, and the held trigger cannot retry until it drops and rises again (`src/main.cpp:1758-1778`, `src/main.cpp:1871-1879`). A normal fast throttle advance can therefore cross the configured AB point while rotor airflow still lags, fail the gate, and remain unlit after N1 becomes ready unless the user pulls below the threshold and pushes through it again. `ABMode::Arming` is defined, serialized, and rendered as “trigger detected, waiting for conditions,” but no runtime path ever assigns it (`src/engine/EngineData.h:8-15`, `src/main.cpp:1932-1941`).

The inverse is also possible. If a pullback or governor action drives protected fuel demand below the same threshold while the stick remains beyond the intended detent, the state machine treats that as trigger release and shuts AB down. If protected demand later recovers above the threshold, it creates a new rising edge and can start another light-up without a new pilot movement. OT-AUD-075 covers the missing hysteresis/minimum-cycle controls; this finding covers the more fundamental ownership error.

Use three explicit stages: **request** from the calibrated pilot control, **permission** from continuously evaluated engine/health gates, and **execution** by the bounded ignition state machine. Before any fuel attempt, a held throttle/switch request may enter the visible Arming state and wait for stable permission for a bounded time; this matches an automatic schedule without surprising the user. Once fuel/ignition has actually been attempted and confirmation fails, latch Failed and require an intentional deselect/reselect. A safety pullback may revoke permission and cut AB, but recovery should not relight until the selected rearm policy is satisfied. Show all three states and the blocking reason.

### OT-AUD-079 — zero Torch EGT Cut has contradictory user and runtime meanings

The Config page presents **Use Torch** as the ignition-method switch and describes **Torch EGT Cut** as the temperature at which the spike is cut, with “0 = disabled” (`data_src/config.html:284-290`, generated equivalent `data_src/pages/config-schema.js:151-157`). In the normal conventions of this page, that means the optional EGT protection is disabled. The block's public member and header comment say the same: `torchTotLimit = 0.0f` is a “safety EGT cap” with “0=disabled” (`src/engine/sequencer/blocks/ABIgnite.h:14-25`).

Runtime has a different contract. `onEnter()` sets `_doTorch = useTorch && torchTotLimit > 0`, so zero skips the entire main-fuel spike, not just the cut (`src/engine/sequencer/blocks/ABIgnite.h:29-46`). If no dedicated igniter is selected, the block faults for having no ignition action; if both methods were selected, only the igniter runs even though the UI still shows Torch enabled. Sequence validation does generate a nonblocking issue saying a positive limit is required (`src/main.cpp:895-906`), but the Config save warnings do not surface this relationship where the contradictory value is entered.

Requiring a valid EGT ceiling for the aggressive torch method is a sensible protection policy, but it must be explicit. Prefer **Torch enabled → a healthy selected EGT and positive cut limit are required**, make the limit required/visible in the same card, reject or require an acknowledged Save-anyway warning there, and display “Torch unavailable” if feedback is absent. If expert sensorless torch is intentionally allowed instead, zero must consistently disable only the cut. In either design, the sequence preview must show which ignition actions will physically run before fuel testing.

### Operator trigger and ignition assessment against established practice

The four trigger sources are all legitimate; they suit different installations. They should select/request afterburner, not directly authorize fuel. Official UK propulsion training describes throttle movement beyond maximum dry power as the pilot's afterburner selection while automatic controls schedule pump/fuel/nozzle behavior from engine and environmental inputs. It also documents both timed spark/pilot-flame ignition and a brief hot-shot of extra engine fuel as real ignition methods. Historical NASA afterburner tests likewise used a prescheduled fuel flow, selector advance, and deliberately delayed torch ignition rather than a raw switch-to-fuel connection. See [UK MOD AP3456 Volume 3, Propulsion](https://assets.publishing.service.gov.uk/media/5e18909040f0b65dc1918760/Volume_03_Propulsion.pdf) and [NASA NACA-RM-E50J10](https://ntrs.nasa.gov/api/citations/19930087619/downloads/19930087619.pdf).

| OpenTurbine trigger | Assessment | Intended user meaning | Sensible default behavior |
|---|---|---|---|
| Manual/browser FIRE | Valid for bench, commissioning, and unusual externally controlled installations; weak as the primary airborne control | An explicit maintenance/operator request | Offer an optional physical arm; display every blocking gate and attempt state; cancel a pending request without a later surprise light |
| Throttle threshold | The most familiar aircraft-like default, but the present implementation needs OT-AUD-078 | Treat a calibrated point near full stick as an AB detent/request, independent of protected main-fuel output | Separate ON/OFF detents with hysteresis; enter visible bounded **Arming** until stable engine permission; after an actual failed light require stick below OFF and back above ON |
| Physical switch | Fully sensible for hobby/DIY aircraft and test stands, particularly as a guarded AB select/master | A dedicated maintained AB selection, not a direct valve command | Debounce/dwell it, optionally combine it with an arm/master, and apply the same continuously evaluated N1/EGT/airflow/health gates as every other source |
| Analog/RC input | Sensible advanced mode for a spare two-/three-position receiver channel or proportional AB control | A separately calibrated AB request/axis, optionally also used to select a pump-demand zone | Require learned endpoints, validity/failsafe behavior, hysteresis, and clear separation between request and pump schedule; signal loss should follow an explicit operator-selected policy |
| AB STOP | Sensible and necessary with every source | Immediate AB-only deselection/cancel | Keep universally authoritative: cancel pending arming, invalidate an older FIRE request, and cut AB fuel without depending on the selected trigger mode |

The actual flame-lighting choices are also conceptually sound. A dedicated igniter is conventional; the main-fuel torch/hot-shot option is a documented method when brief, bounded, and coordinated; using both is a plausible high-energy DIY option when individually timed and proven. “Timed assumption” is not an ignition source—it is a choice to proceed without combustion proof—so it should remain available for expert/sensor-light builds but be labelled as unverified and constrained by the independent maximum unconfirmed-fuel deadline in OT-AUD-074.

A useful operator state model is **DISARMED → ARMED → REQUESTED/WAITING** (with the exact gate reason) **→ IGNITING → LIT**, with **FAILED — RELEASE TO RETRY** only after an actual fuel/ignition attempt. A blocked pre-attempt request should be allowed to become ready while held for a short configured window; an attempted-and-failed ignition should not silently retry. JetCat's LCU is only an afterburner-light accessory, not a fuel afterburner controller, but its published convention—full throttle request plus confirmed maximum engine speed before activation—is relevant evidence that hobby users already understand request-plus-engine-state gating. See [JetCat LCU Pro V2](https://www.jetcat.de/en/productdetails/produkte/jetcat/produkte/zubehoer/LED-%20I-O%20Platine/LCU%20PRO-V2).

### OT-AUD-008/009 — green gates omit important executable coverage

`tools/run_release_checks.py` runs PCB-profile and wiring-verifier tests, but `.github/workflows/ci.yml` and `.github/workflows/release.yml` do not run `tools/test_pcb_profile.py` or `dev/bench/harness/test_verify_wiring.py`. This is especially important because v2.0.1 changed the profile/compiler and wiring paths.

`tools/sensor_protocol_vectors.cpp` contains 14 host assertions but is not invoked by the local release gate, CI, or release workflow. This is a partial rather than total gap: `src/hal/sensors/SensorProtocolDecode.h:52-68` has a seven-case `constexpr` `selfTest()` guarded by `static_assert`, and `src/main.cpp:20` includes the header, so both successful firmware builds compile and execute that smaller set at compile time. The standalone file adds fault-bit, CRC-failure, positive HX711, and extra temperature cases that are still omitted.

The existing safety regression audit is largely source-pattern validation. No PlatformIO/native executable unit-test target exercises the actual C++ control-loop state transitions. Pattern checks can prove that named guards exist but cannot prove that later assignments do not undo them; OT-AUD-001 is a concrete example.

### OT-AUD-010/011 — manifest and repository controls

The release manifest records firmware byte counts but not a SHA-256 and runtime build ID for each individual firmware image. The outer archive hash is valid, and the official PCB profile SHA-256 regenerated locally exactly matches the published profile (`eb6cd99a...`), but individual identity should still be explicit.

At audit time, `main` had no branch protection/ruleset, the release tag/commit was unsigned, the GitHub release was mutable, and Dependabot security updates, secret scanning, and push protection were disabled. GitHub Actions dependencies are referenced by floating major tags rather than immutable commit SHAs.

Firmware libraries are pinned to explicit versions, and PlatformIO itself is pinned in CI, which materially narrows dependency drift. The remaining build inputs are not fully reproducible or independently authenticated: `platformio.ini` downloads the pioarduino platform from a versioned GitHub release-asset URL without a checked digest, the workflows use floating action major tags, and the Jekyll site declares unbounded `github-pages`, `jekyll-seo-tag`, and `jekyll-sitemap` gems without a committed lockfile. Record hashes/locks for every executable build input, pin actions to reviewed commit SHAs, and generate the release SBOM/provenance from those exact inputs.

### OT-AUD-012 — release communication inconsistencies

The public v2.0.1 release body contains only an automatically generated changelog link, with no upgrade instructions, safety limitations, known issues, exact target mapping, or rollback procedure. `CHANGELOG.md` describes a signed firmware/dashboard package even though the package/executable is not signed. `docs/SETUP_TOOL.md` says signing is mandatory while the workflow makes it optional. These should agree with the artifacts testers actually receive.

## Hardware-free two-day plan

### Day 1 — make the control behavior provable

- **OT-FINAL-001 — Option 1:** use one transport-neutral core-output adapter. Route the final semantic Prop Pitch and Bleed Valve demand to the effective local or I2C driver, with identical governor/sequence/rule/tool behavior on both ESP targets. Prop Pitch remains 0% fine/minimum load and 100% coarse/maximum load; its configured parked demand applies during initialization and standby, while Reduced-Power, feedback loss, and fault retain the fixed coarse-safe command. Bleed Valve remains 0% closed and 100% open. Add local/I2C parity tests for normal commands, initialization, standby, limp, fault, and device loss.
- **OT-FINAL-002 — clean standardization:** remove the historical rotated Bleed Valve type convention and obsolete translation code. Use the same canonical output-driver model as the rest of the registry: Servo, PWM, Relay, and I2C Relay mean their actual electrical drivers everywhere in validation, serialization, UI, migration/import, runtime initialization, tools, and sequences. The modern registry is the truthful authority; do not retain incorrect behavior merely for compatibility. Keep only a minimal one-time import conversion if needed to recognize an old file unambiguously, then save it in the canonical form. Add driver-table tests on both ESP targets.
- **OT-FINAL-003 — unified igniter operation:** keep one semantic Off/On igniter command for primary and afterburner ignition. Convert it to the selected local or I2C driver's electrical state, including Active high/Active low, exactly once at the final output boundary. Use the same authority for pre-initialization parking, initialization, normal commands, shutdown/fault, all-off, and reboot preparation; remove stale parallel polarity state where it is no longer needed. The UI must state that Active high means HIGH=energized and Active low means LOW=energized. Cover both igniters, both polarities, and every supported relay transport on both ESP targets.
- **OT-FINAL-004 — Option 1:** preserve negative afterburner main-fuel coordination, but when main fuel is already running, clamp the AB-adjusted command at the calibrated reliable running minimum. Authoritative zero from STOP, fault, shutdown, combustion cut, or an already-off main-fuel command remains exactly zero and is never lifted. Positive AB coordination remains unable to exceed an active protection-owned command or Reduced-Power cap. Show a concise warning/preview when the configured negative offset would reach the floor, without blocking an otherwise valid value. Add boundary tests immediately below/at/above the minimum for positive, zero, and negative offsets and every hard-cut state.
- **OT-FINAL-005 — simple authoritative master:** the one visible Oil Pressure Loop switch is authoritative. Effective loop ownership, actuation, feedback requirements, validation, status, and rule/sequence conflict checks require both the master and a valid saved loop definition. Firmware must not promote enabled saved entries over an explicitly disabled master. Do not add per-loop enable controls or extra UI clutter without a demonstrated later need.
- **OT-FINAL-006 — Option 2 with driver-aware UI:** every on/off oil-pump driver, local or I2C and primary or secondary, treats fallback zero as Off and any positive fallback as On. Once Reduced-Power is active, further ordinary sensor losses retain its established continue-running behavior; critical stop/control-path loss still shuts down. - Output inversion is not generally double-applied: the current local relay, PWM, servo, and I2C boundaries each perform their own one-time electrical transformation. The confirmed exceptions above arise from semantic routing/type selection, not a universal inversion failure.

### Accepted corrections for OT-FINAL-014 through OT-FINAL-026 - 2026-08-08

All thirteen findings above are now corrected in software and have dedicated regression coverage. They remain subject to the full HIL campaign before release.

- OT-FINAL-014/015: RUNNING Developer Mode can publish only the established live-safe Config fields. The response now waits for the exact Core-1 apply generation before reporting success and rebasing the browser.
- OT-FINAL-016: Pitch Gain remains live-tunable only while it preserves the current governor actuator authority. Crossing zero is rejected until the turbine is stopped.
- OT-FINAL-017: relay oil pumps use the persisted on/off enum and 0/100 hysteretic behavior during cooldown and standby windmilling pressure control; proportional pumps retain proportional behavior.
- OT-FINAL-018: a standard registry Bleed Valve is routed by its canonical `bleed_valve` ID as well as the compatible purpose, including I2C operation and safe-state handling.
- OT-FINAL-019/025/026: TLA2528 threshold switches and torque are accepted and consumed by their real runtime paths, while each I2C driver is restricted to the address family the device manager can actually service.
- OT-FINAL-020: a registry Start Fuel channel is the authoritative wet-glow fuel output. The obsolete duplicate GPIO path is suppressed and output semantics come from the selected driver.
- OT-FINAL-021: local PWM-capable igniters retain the advanced dwell/current-limited modes. Local relay and TCA9554 relay igniters expose Simple On/Off only; incompatible imported settings are normalized to Simple and the Hardware page explains the capability.
- OT-FINAL-022: native GPIO inhibit, E-stop, fault, and enabled oil-safety inputs are checked from their physical asserted state before START, matching registry input behavior.
- OT-FINAL-023: a fitted but unhealthy physical throttle source always means no throttle-triggered afterburner request. Engine-demand fallback is used only when no physical operator-throttle source is configured.
- OT-FINAL-024: registry oil-pressure feedback has precedence over the legacy ADC adapter from initialization through runtime use, so it cannot be overwritten or recalibrated through an unrelated path.
